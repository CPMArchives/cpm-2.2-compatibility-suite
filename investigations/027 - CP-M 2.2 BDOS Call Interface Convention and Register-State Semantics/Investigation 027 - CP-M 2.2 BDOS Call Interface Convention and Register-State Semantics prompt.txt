OBJECTIVE

Define the general CP/M 2.2 BDOS calling convention and return-state
contract.

Previous investigations established individual BDOS function behavior.

Investigation 027 determines the common interface rules surrounding every
BDOS call:

- how applications invoke BDOS;
- which registers provide parameters;
- which registers return results;
- which registers are preserved;
- which values are undefined;
- what happens for unsupported function numbers;
- what applications may safely assume after BDOS returns.

The goal is to define the BDOS compatibility boundary without requiring
private DRI implementation details.

KEY QUESTIONS


1. BDOS ENTRY MECHANISM

Determine:

- how applications invoke BDOS;
- role of address 0005h;
- relationship between CALL 0005h and the BDOS entry vector;
- whether applications may call BDOS directly elsewhere.

Determine what is REQUIRED versus DRI-specific.


2. FUNCTION NUMBER PASSING

Determine:

- C register semantics;
- valid function range;
- behavior above the implemented range;
- behavior of reserved functions.


3. PARAMETER PASSING

Determine:

- DE parameter semantics;
- whether HL or other registers may be used;
- whether unused registers must contain defined values.

Avoid requiring implementation details.


4. RETURN VALUE CONVENTION

Determine:

- A return value behavior;
- HL return behavior;
- relationship between A and L;
- B register behavior;
- functions returning values in other registers.


5. REGISTER PRESERVATION

Determine:

After BDOS returns:

- which registers are preserved;
- which registers may be destroyed;
- whether preservation differs by function;
- whether applications may rely on undocumented preservation.


6. STACK BEHAVIOR

Determine:

- whether BDOS preserves caller stack;
- whether BDOS may alter SP temporarily;
- return mechanism;
- nested-call assumptions.


7. UNSUPPORTED FUNCTIONS

Determine:

- return values;
- whether unsupported calls return;
- whether they terminate;
- whether behavior differs between DRI source and documentation.


8. INVALID PARAMETERS

Determine:

- invalid drive;
- invalid user;
- invalid FCB;
- invalid memory pointer;
- invalid function parameters.

Separate:

normal returned errors

from:

fatal/operator diagnostics.


9. BDOS REENTRANCY

Determine:

- whether BDOS may be called recursively;
- whether interrupts or resident extensions may safely enter BDOS;
- what state assumptions exist.

Do not design BetterCP/M behavior.


10. DRI SOURCE ANALYSIS

Review BDOS source for:

- entry sequence;
- register handling;
- return paths;
- common epilogue.

Extract only compatibility-relevant behavior.

FINAL GOAL

Define the CP/M 2.2 BDOS application interface contract:

When a program executes CALL 0005h,
what must a compatible BDOS accept,
what must it return,
and what machine state may the caller rely upon afterward?

BetterCP/M implementation without requiring reproduction of DRI-private
implementation details.
