INVESTIGATION 024 — CP/M 2.2 Transient Program Lifecycle, Termination,
and BDOS Return-State Semantics

Continue the BetterCP/M CP/M 2.2 compatibility investigation series.

Investigation 023 is complete.

The authoritative Compatibility Ledger currently incorporates findings
through Investigation 023.

Do not modify the Compatibility Ledger.

Do not modify previous investigation reports, architecture documents,
roadmaps, specifications, or other existing BetterCP/M files.

Create Investigation 024 as a new evidence report with its own directory
and preserved experimental artifacts.

This is an evidence investigation only.
Do not implement BetterCP/M changes.


OBJECTIVE

Establish the externally visible lifecycle contract of a CP/M 2.2 transient
program after it begins execution.

Investigation 022 established:
- transient lookup;
- COM loading;
- DMA restoration;
- CALL 0100h transfer.

Investigation 023 established:
- transient entry memory;
- command tail;
- default FCBs;
- page-zero entry state;
- entry return environment.

Investigation 024 begins after the transient program receives control.

Determine:

- how transient programs normally return control to CCP;
- how different termination paths behave;
- what state CCP/BDOS preserves or restores;
- what state applications may rely upon after termination;
- which termination behaviors are CP/M compatibility requirements;
- which are DRI implementation details.

SCOPE

Investigate transient lifecycle events:

- normal RET termination;
- BDOS Function 0 termination;
- JMP 0000h termination;
- warm boot behavior;
- abnormal BDOS failures where visible;
- termination after changing drive/user state;
- termination after changing DMA;
- termination after modifying page zero;
- termination after opening files;
- termination after using console and disk services.

The investigation concerns the boundary between:

    transient program
            |
            v
    CCP / BDOS / BIOS environment


NON-GOALS

Do not investigate:

- application-specific behavior;
- language runtime conventions;
- compiler-generated termination code;
- CP/M 3 or MP/M behavior;
- BetterCP/M implementation design;
- multitasking;
- memory protection.

Do not assume that a behavior is required simply because common programs
perform it.


KEY QUESTIONS


1. RET TERMINATION

Determine the exact CP/M 2.2 RET termination contract.

Establish:

- where CCP places the return address;
- what state RET restores;
- whether RET requires a valid stack;
- whether CCP regains control without WBOOT;
- drive/user state after RET;
- DMA state after RET.

Distinguish:

    application-visible behavior

from:

    private CCP stack organization.


2. BDOS FUNCTION 0 TERMINATION

Determine:

- how Function 0 terminates a transient;
- whether CCP is reloaded;
- whether BIOS WBOOT occurs;
- what state is preserved;
- what state is reconstructed.

Compare with RET.


3. JMP 0000H TERMINATION

Determine:

- what happens when a transient jumps to address 0000h;
- whether the warm-start vector is invoked;
- whether CCP is restored;
- whether user/drive state changes;
- whether disk state changes.

Compare with RET and Function 0.


4. TERMINATION STATE COMPARISON

Create a matrix:

                RET
                BDOS 0
                JMP 0000h

For each record:

- CCP return path;
- WBOOT involvement;
- page-zero state;
- drive/user state;
- DMA state;
- open-file state;
- console state;
- observable differences.


5. DRIVE AND USER STATE

A transient may change:

- current drive;
- current user area.

Determine:

- what survives RET;
- what survives Function 0;
- what survives JMP 0000h;
- what CCP restores;
- what BDOS preserves.

Cross-check Investigation 007 and 023.


6. DMA STATE

A transient may change DMA through BDOS Function 26.

Determine:

- DMA state after RET;
- DMA state after Function 0;
- DMA state after JMP 0000h;
- whether CCP restores 0080h;
- whether applications may rely on restored DMA.

Do not duplicate I023 initial DMA findings.


7. PAGE ZERO MODIFICATION

Determine what happens if a transient modifies:

- 0000h;
- 0003h;
- 0004h;
- 0005h.

Establish:

- whether CCP overwrites these on return;
- whether WBOOT reconstructs them;
- whether RET differs from warm restart.


8. FILE AND DISK STATE

Determine visible effects of termination after:

- opening files;
- writing files;
- leaving FCBs modified;
- changing DMA.

Do not investigate BDOS file semantics themselves.

Only determine lifecycle cleanup behavior.


9. CONSOLE STATE

Determine whether termination restores:

- console echo state;
- output mode;
- LIST state;
- IOBYTE routing.

Cross-check Investigation 018.


10. ERROR AND ABNORMAL PATHS

Investigate visible behavior for:

- invalid BDOS calls;
- invalid termination state;
- stack corruption where safely testable.

Do not intentionally corrupt the emulator or host environment.

The goal is observable CP/M behavior, not crash testing.


11. CCP SOURCE ANALYSIS

Review DRI CCP source to determine:

- RET return path;
- Function 0 handling;
- warm-start handling;
- saved state assumptions.

Do not produce a source commentary.

Extract only compatibility-relevant behavior.

FINAL GOAL

Determine the CP/M 2.2 transient lifecycle contract:

    After a program begins execution,
    how does it return control,
    what state survives,
    what state is restored,
    and what behavior must a compatible implementation provide?

The result should define the application-visible lifecycle boundary
without requiring BetterCP/M to reproduce every internal DRI CCP/BDOS
implementation detail.
