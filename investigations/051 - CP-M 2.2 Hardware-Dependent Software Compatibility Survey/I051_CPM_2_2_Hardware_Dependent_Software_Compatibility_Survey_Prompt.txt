OBJECTIVE

Determine the compatibility boundary between CP/M 2.2 software
compatibility and hardware-dependent software behavior.

Previous investigations established:

- CP/M interfaces;
- BIOS behavior;
- communications software assumptions;
- application compatibility requirements;
- direct system access behavior.

Investigation 051 examines software that bypasses or extends CP/M
abstractions by depending on specific hardware characteristics.

Investigate:

- hardware-specific utilities;
- machine-specific applications;
- direct hardware access;
- custom BIOS assumptions;
- peripheral dependencies.

Determine:

- which behaviors belong to the CP/M compatibility contract;
- which behaviors belong to hardware compatibility profiles;
- which behaviors are not required for CP/M compatibility.


COMPATIBILITY STANDARD

Consider:

- documented CP/M 2.2 behavior;
- Digital Research implementation behavior;
- common CP/M programming practices;
- historically significant software dependencies.

Distinguish between:

- CP/M environment assumptions;
- BIOS extension assumptions;
- hardware-specific assumptions.

Do not assume hardware-dependent behavior is required without evidence.

INVESTIGATION QUESTIONS

1. SOFTWARE CORPUS

Identify representative hardware-dependent CP/M software.

Record:

- software name;
- version or release where available;
- source/archive location;
- hardware target;
- category;
- evidence collected.


2. HARDWARE DEPENDENCY TYPES

Determine dependencies involving:

- direct I/O ports;
- memory-mapped hardware;
- custom BIOS calls;
- interrupt behavior;
- display hardware;
- storage controllers;
- serial hardware.


3. CP/M VERSUS HARDWARE BOUNDARY

Determine:

- whether software depends on CP/M semantics;
- whether it depends on BIOS behavior;
- whether it depends on a specific machine;
- whether compatibility belongs in the CP/M contract or hardware profile.


4. DIRECT HARDWARE ACCESS

Determine:

- common direct hardware access patterns;
- whether such access was widespread;
- whether software replacement or hardware profiles are appropriate.


5. BIOS EXTENSION USAGE

Determine:

- use of non-standard BIOS extensions;
- common conventions;
- compatibility implications.


6. EXPERIMENTAL REQUIREMENTS

Create deterministic validation tests covering:

- representative hardware-dependent software;
- standard CP/M environment behavior;
- hardware-specific behavior;
- failure or unsupported cases.

Each test must include:

- software tested;
- hardware assumptions;
- purpose;
- procedure;
- observed behavior;
- compatibility classification.


7. CONTROLLED TEST MATRIX

Include:

- standard CP/M interfaces;
- BIOS extensions;
- direct hardware access;
- machine-specific behavior;
- unsupported hardware assumptions.
