INVESTIGATION 022 — CP/M 2.2 CCP Transient Program Lookup, Loading,
and Execution Semantics

Continue the BetterCP/M CP/M 2.2 compatibility investigation series.

Investigation 021 is complete.

The authoritative Compatibility Ledger is now:

    02 Compatibility Ledger - Investigation 021.txt

It incorporates findings through Investigation 021 and currently ends at
entry 0491.

Do not modify the Compatibility Ledger.

Do not modify any previous investigation report, architecture document,
roadmap, source archive, or other pre-existing BetterCP/M file.

Create Investigation 022 as a new evidence report with its own directory
and associated probe/harness artifacts.

This is an EVIDENCE INVESTIGATION, not BetterCP/M implementation work.


OBJECTIVE

Establish the CP/M 2.2 Console Command Processor transient-program lookup,
loading, execution, and immediate return/error contract.

Investigation 021 established the common CCP command-processing path through:

    command acquisition
        |
        v
    normalization and parsing
        |
        v
    built-in recognition
        |
        +----------------------+
        |                      |
        v                      v
    built-in command       transient candidate

Investigation 001 established the transient environment after successful
loading and immediately before/at transfer to 0100h.

Investigation 022 must characterize the path between those two established
boundaries:

    transient candidate
        |
        v
    executable file specification
        |
        v
    drive/user context
        |
        v
    Open / lookup
        |
        v
    sequential load into TPA
        |
        v
    EOF / size / capacity handling
        |
        v
    final transient-entry preparation
        |
        v
    transfer to 0100h
        |
        v
    transient termination / CCP recovery

The investigation should determine the smallest externally observable
contract BetterCP/M must reproduce without turning the DRI CCP's particular
internal loader implementation into a compatibility requirement.

SCOPE BOUNDARY

Investigation 022 includes:

    transient executable name formation
    COM extension handling
    drive selection for lookup
    user-area context for lookup
    file Open behavior used by CCP
    sequential loading
    load address progression
    record-size behavior
    EOF handling
    TPA capacity behavior
    zero-length and malformed executable cases where meaningful

    immediate loader failure behavior

Investigation 022 does NOT attempt to investigate the detailed semantics of:

    DIR
    ERA
    REN
    SAVE
    TYPE
    USER

Those remain separate CCP resident-command subjects.

It also does not re-investigate the general BDOS Open, Read Sequential,
DMA, or error contracts already established. It should determine how the
CCP uses those contracts to implement transient execution.


QUESTIONS TO RESOLVE


1. TRANSIENT-CANDIDATE INPUT TO THE LOADER

Begin at the boundary established by Investigation 021.

Determine exactly what information the loader receives when the command is
not recognized as a built-in.

Establish:

- representation of the parsed command name;
- whether the name is already uppercase;
- whether a drive prefix has already been resolved;
- whether the extension field is empty, explicit, or synthesized;
- whether default FCBs have already been constructed;
- whether the transient command tail has already been constructed;
- what current drive is in effect;
- what user number is in effect.

Do not duplicate Investigation 021 findings. Record them only insofar as
they define the loader's inputs.


2. EXECUTABLE FILE SPECIFICATION

Determine precisely how DRI CCP constructs the executable file
specification.

Establish:

- whether `.COM` is inserted by CCP;
- whether the executable type is always COM;
- whether the caller may explicitly type `.COM`;
- what happens with an explicit non-COM extension;
- whether a command with an explicit extension is transformed before Open;
- whether the filename is represented as an FCB;
- exact filename/type fields passed to BDOS Open;
- drive-byte treatment.

Trace DRI CCP source rather than assuming behavior from modern shell
conventions.


3. COMMAND NAME LENGTH AND 8.3 INTERACTION

Determine how the command token maps onto CP/M's 8.3 filename model.

Establish:

- maximum executable basename length;
- behavior of names shorter than eight characters;
- behavior of names exactly eight characters;
- behavior of names longer than eight characters;
- whether excess characters are rejected, truncated, or parsed differently;
- interaction with an explicit period/type;
- whether malformed executable names reach BDOS Open.

Cross-check Investigation 021's command-token parsing findings and
Investigation 008's FCB filename semantics.


4. CURRENT-DRIVE TRANSIENT LOOKUP

For an unprefixed transient command such as:

    FOO

determine:

- which drive is searched;
- whether only the current drive is searched;
- whether any automatic multi-drive search exists;
- whether any system drive is searched;
- whether user 0 receives special search treatment;
- whether lookup remains within the current user area;
- what happens when FOO.COM exists elsewhere but not in the active
  drive/user context.

Do not import later ZCPR/Z-System path-search behavior into CP/M 2.2.


5. EXPLICIT-DRIVE TRANSIENT LOOKUP

For a command such as:

    B:FOO

determine:

- whether FOO.COM is looked up on B:;
- whether the current drive is temporarily or persistently changed;
- whether BDOS Function 14 is used;
- whether page-zero 0004h reflects the command drive during execution;
- what default FCB drive bytes reflect;
- what happens after the transient terminates;
- whether the original drive is restored;
- whether behavior differs after RET, Function 0, and JMP 0000h
  termination.

Cross-check Investigation 021's drive-prefixed command behavior.

Do not assume that lookup drive, command-entry default drive, and persistent
CCP current drive are necessarily the same concept.


6. USER-AREA LOOKUP

Determine the role of the current CP/M user number in transient lookup.

Establish:

- whether CCP searches only the current user area;
- whether user 0 receives any fallback or privileged search;
- whether a program in another user area can be executed without first
  changing user;
- whether an explicit drive prefix affects user-area lookup;
- what user number the transient sees during execution;
- whether termination preserves the user number.

Use controlled copies of disks with uniquely marked COM files in different
user areas if necessary.

Do not infer later CP/M variants' search behavior.


7. BDOS OPEN USED BY CCP

Trace the DRI CCP executable Open operation.

Determine:

- which BDOS function is called;
- exact FCB state supplied;
- expected success/failure result;
- whether extent/module fields are initialized in a particular way;
- whether the CCP depends upon undocumented Open side effects;
- what state from the opened FCB is subsequently used by the loader.

Do not duplicate Investigation 008's general Open contract.

Create a new ledger proposition only if CCP imposes an independently
observable requirement not already captured there.


8. LOADER DMA STRATEGY

Determine how CCP uses DMA while loading a COM file.

Establish:

- initial DMA address used for the first program record;
- whether DMA is set to 0100h before the first read;
- how DMA advances for successive records;
- whether DMA advances in 128-byte increments;
- whether the CCP resets DMA to 0080h before transferring control to the
  transient;
- relationship to Investigation 001's REQUIRED default-DMA-at-entry
  proposition;
- what happens to command-tail data at 0080h while loading.

This is a key boundary question.

Investigation 001 established that the transient begins with default DMA at
0080h and the command tail in the same buffer. Investigation 022 should
determine how CCP preserves/restores that state while loading program data.


9. LOAD ORIGIN

Confirm from loader behavior, not merely final observation, that the first
128-byte executable record is placed beginning at:

    0100h

Cross-check existing ledger entries rather than duplicating them.

Determine whether the loader computes this address from a symbolic TPA base
or uses a fixed 0100h assumption.

Only the externally required result belongs in the Compatibility Ledger.


10. SUCCESSIVE RECORD PLACEMENT

Determine how subsequent 128-byte records are placed.

Establish:

- exact address progression;
- whether records are contiguous;
- whether any gaps are inserted;
- whether every successful sequential read advances the destination by
  0080h;
- what happens to the final partial logical record;
- whether CCP clears bytes beyond physical EOF inside the final 128-byte
  record.

Be careful: CP/M files are record-oriented, and directory length metadata
does not generally preserve an arbitrary byte-precise host-file EOF.

Do not impose modern byte-stream semantics on COM loading.


11. SEQUENTIAL READ LOOP

Trace the DRI CCP load loop.

Determine:

- use of BDOS Function 20;
- interpretation of A=00h success;
- interpretation of A=01h EOF;
- handling of other return values;
- whether the loader closes the executable before execution;
- whether Close is necessary;
- whether the loader uses random access or file-size calls at any point.

Cross-check Investigations 008, 010, and 015.

The objective is CCP loader behavior, not re-documentation of Function 20.


12. END-OF-FILE HANDLING

Determine what terminates successful loading.

Establish:

- whether the first sequential-read EOF ends the load;
- whether EOF itself is considered successful;
- whether a file containing exactly N records produces N loaded records;
- whether a zero-record executable can be opened and what happens next;
- whether the loader distinguishes logical EOF from a physical read error.

If zero-length COM files cannot be represented straightforwardly in the
reference CP/M file system, document that limitation rather than inventing a
test.


13. FINAL PARTIAL RECORD SEMANTICS

Investigate the last CP/M record carefully.

Because CP/M files are represented in 128-byte records, determine:

- what bytes are loaded for the final record;
- whether CCP has any byte-count information below the 128-byte level;
- whether unused bytes are whatever is physically stored in the final
  record;
- whether any clearing or padding is performed by CCP;
- whether a transient may observe bytes beyond the intended program's
  logical machine-code end.

Classify any stale/padding behavior conservatively.

Do not require exact residual bytes unless CP/M actually defines them.


14. MAXIMUM LOADABLE TRANSIENT SIZE

Determine how CCP prevents a COM file from overwriting resident CP/M.

Establish:

- how the upper load boundary is determined;
- relationship to the BDOS entry address at page-zero 0005h;
- relationship to the TPA upper boundary established in Investigation 001;
- whether CCP checks destination before each read;
- whether it permits a record whose end exactly reaches the allowed
  boundary;
- whether the check is record-granular;
- maximum loadable COM size in the reference configuration;
- which part is configuration-specific versus universally semantic.

Do not turn the reference system's numeric BDOS address or TPA size into a
portable requirement.


15. OVERSIZE COM FILE

Construct a controlled executable larger than the available transient
program area.

Determine:

- whether CCP detects the condition before overwriting BDOS;
- exact point at which it detects it;
- whether the excessive record is read;
- whether resident memory is preserved;
- whether execution is suppressed;
- error presentation;
- recovery to the command loop;
- disk/current-drive/user state after failure.

Use a safe deterministic fixture.

Do not risk the authoritative reference disk or project files.


16. EXACT-BOUNDARY COM FILE

If practical, construct controlled COM files near the maximum loadable size.

Test at least:

    largest clearly valid size
    first clearly invalid size

and, if the source reveals an interesting boundary:

    exactly one record below limit
    exactly at limit
    one record beyond limit

The purpose is to establish comparison semantics and record granularity, not
merely the approximate maximum size.


17. LOAD FAILURE FROM MISSING FILE

Investigation 021 established generic unrecognized-command behavior.

Investigation 022 should now trace the missing transient through the actual
Open attempt.

Determine:

- exact FCB presented to Open;
- Open return value;
- whether any additional lookup is attempted;
- whether another drive or user area is searched;
- transition to the generic CCP error path;
- whether DMA or other state is restored before the next prompt.

Do not duplicate I021's presentation proposition unless new evidence changes
it.


18. READ ERROR DURING LOAD

Where safely testable, force a read failure after successful Open.

Determine:

- whether CCP distinguishes physical/read failure from ordinary EOF;
- whether BDOS itself intercepts the physical error under the semantics
  established by Investigation 015;
- whether CCP receives control again;
- whether partial program contents are ever executed;
- recovery behavior.

If Investigation 015 already makes the result inevitable and a new
experiment adds no value, use source analysis instead and state why.


19. PROGRAM EXECUTION TRANSFER

Trace the final successful loader steps immediately before execution.

Determine:

- restoration of DMA to 0080h;
- final default-FCB state;
- final command-tail state;
- stack setup;
- creation of the valid RET return word;
- CALL versus JP transfer to 0100h;
- relationship to Investigation 001's observed entry SP and return address;
- whether any registers are deliberately established;
- whether interrupts are deliberately changed.

Do not duplicate Investigation 001's entry propositions.

Instead, use I022 to strengthen their evidence where appropriate.


20. CALL 0100h AND RET RETURN PATH

Investigation 001/I002 established that RET termination is valid.

Trace the CCP mechanism beneath it.

Determine:

- whether DRI CCP executes CALL 0100h;
- where the return address leads;
- what CCP does immediately after RET;
- whether RET returns directly to the command loop or through cleanup;
- whether drive/user/DMA state is repaired;
- whether CCP invokes warm boot after RET;
- whether the command is re-prompted without WBOOT.

This is likely to provide stronger evidence for existing transient-return
ledger entries.

Do not require the exact numeric CCP return address.


21. BDOS FUNCTION 0 TERMINATION PATH

Trace a transient that terminates through BDOS Function 0.

Determine:

- whether Function 0 invokes BIOS WBOOT;
- whether CCP is reloaded/re-entered;
- whether the path differs observably from RET;
- whether command environment state differs;
- what drive/user state survives;
- what page-zero/DMA state is reconstructed.

Cross-check Investigations 001, 007, and 020.

Only create new propositions for genuinely new externally visible
distinctions.


22. JMP 0000h TERMINATION PATH

Likewise trace:

    JMP 0000h

Determine its relationship to:

    page-zero WBOOT vector
    BIOS WBOOT
    CCP re-entry
    disk/login state
    DMA restoration
    prompt recovery

Cross-check existing ledger entries rather than duplicating them.


23. RETURN-PATH COMPARISON

Using small deterministic marker programs, compare:

    RET
    BDOS Function 0
    JMP 0000h

Record externally visible post-termination state, including where useful:

    current drive
    user number
    prompt
    page-zero vectors
    DMA behavior
    disk login state

The purpose is not to prove they are internally identical. Determine which
observable consequences are required to be equivalent and which differ.


24. PROGRAM THAT FALLS THROUGH

Construct, only if safe and diagnostically useful, a controlled program whose
execution does not terminate normally but falls beyond its intended bytes.

Determine whether CP/M defines any protection against this.

Most likely this is simply erroneous application behavior.

Do not turn crash behavior into a compatibility requirement unless primary
evidence establishes one.

This test may be omitted if it adds no compatibility information.


25. EMPTY OR MINIMAL TRANSIENT

Test the smallest meaningful transient programs.

Examples:

    RET

and, where representable:

    a one-record file beginning with RET

Use these to verify:

    load origin
    execution transfer
    return path
    final DMA
    command-tail preservation

Do not duplicate existing propositions merely because the fixture confirms
them.


26. PROGRAM SELF-OBSERVATION PROBE

Create or reuse a small transient probe that records the entry environment
after being loaded through the ordinary CCP path.

Where useful capture:

    SP and return word
    0000h vector
    0003h IOBYTE
    0004h command-entry drive
    0005h BDOS vector
    default FCB 1
    default FCB 2
    0080h command-tail count
    0081h onward
    initial DMA behavior

Use this primarily to connect loader findings to Investigation 001.

Do not re-open settled questions unless I022 evidence conflicts with them.


27. LOAD-MEMORY OBSERVATION

Construct deterministic COM images containing recognizable per-record
patterns.

For example, use distinct markers in successive 128-byte records so the
loaded memory can demonstrate:

    record 0 -> 0100h
    record 1 -> 0180h
    record 2 -> 0200h
    ...

Choose a safe observation technique that does not itself overwrite the
memory being measured.

Preserve source/generator and exact binary hashes.


28. USER-AREA FIXTURE

If needed, create identical command names with distinct marker programs in
different user areas.

Use this to determine exactly which program CCP executes under different
current-user settings.

Preserve:

    before image
    after image
    directory listings by user
    command transcript
    marker output
    hashes


29. DRIVE-LOOKUP FIXTURE

Likewise, where needed, create same-named marker programs on different
drives.

Determine:

    unprefixed lookup
    explicit-drive lookup
    persistent current drive after return
    command-entry drive byte
    default-FCB drive interpretation

Use copies of reference disks and preserve before/after evidence.


30. CCP RELOAD VERSUS PERSISTENCE

Determine what happens to CCP itself across transient execution.

Distinguish:

    ordinary CALL 0100h / RET
        from
    WBOOT-based termination

Establish from source and experiment:

- whether CCP remains resident during ordinary transient execution;
- whether transient loading can overwrite any portion of CCP;
- whether WBOOT reloads CCP in the reference system;
- whether the requirement is that CCP be restored, rather than that a
  particular physical reload mechanism be used.

This distinction is important for BetterCP/M.

Do not require historical floppy-sector reload mechanics if only the
resulting command-environment restoration is compatibility-visible.


31. CCP/BDOS MEMORY BOUNDARY

Determine how the loader protects the resident system.

Establish whether the CCP loader's upper-bound calculation is tied to:

    BDOS entry address
    CCP location
    BIOS location
    another system variable

Separate:

    portable semantic requirement:
        transient loading must not destroy the resident system

from:

    DRI implementation mechanism:
        exact arithmetic/address comparison used by CCP

Do not turn an implementation technique into a compatibility proposition
unless software can observe it.

REFERENCE-ENVIRONMENT LIMITATIONS

The reference z80pack environment has a particular:

    TPA size
    CCP address
    BDOS address
    BIOS address
    disk geometry
    set of available drives
    set of installed COM files
    user-area contents
    WBOOT implementation

None of those numeric or physical details becomes a universal CP/M 2.2
requirement merely because it is observed.

Prefer symbolic/relative conclusions such as:

    first transient byte is loaded at 0100h
    successive records occupy successive 128-byte locations
    loader must not overwrite the resident system

rather than:

    maximum COM size is exactly N bytes on every CP/M system

unless documentation actually establishes a universal value.


EXPERIMENTAL REQUIREMENTS

All experiments must be deterministic and reproducible.

Prefer scripted command input and automatically captured output.

Use generated marker COM files where useful.

For load-boundary experiments:

- work only from copied disk images;
- preserve original images;
- use deterministic generated COM contents;
- record exact file record counts and sizes;
- hash every fixture;
- verify the reference system remains intact after failure tests.

For user/drive lookup experiments:

- preserve directory listings;
- use uniquely identifiable marker programs;
- record user number and selected drive explicitly.

For memory observations:

- use recognizable patterns;
- avoid observation techniques that overwrite the memory under test;
- preserve raw dumps separately from interpretation.

Verify byte-identical probe rebuilds where practical.
