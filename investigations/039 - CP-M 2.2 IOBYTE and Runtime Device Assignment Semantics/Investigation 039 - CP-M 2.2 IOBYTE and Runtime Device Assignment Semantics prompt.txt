compatibility contract.

- BDOS character-device behavior;
- BIOS character-device behavior;
- IOBYTE definitions;
- device interfaces;
- character-device runtime semantics.


Investigation 039 determines how CP/M software interacts with dynamic
device assignment and whether historical software depends upon specific
IOBYTE behavior.

Investigate:

- logical device assignment;
- physical device mapping;
- runtime device switching;
- STAT DEV behavior;
- application-visible device state;
- software assumptions about redirected devices.


Determine:

- which IOBYTE behaviors are compatibility requirements;
- which device-assignment behaviors are implementation-specific;
- which historical conventions must be preserved for software
  compatibility.

INVESTIGATION QUESTIONS


1. IOBYTE COMPATIBILITY BOUNDARY

Determine whether IOBYTE is only a BDOS/BIOS mechanism or a practical
software compatibility interface.

Investigate:

- application access to IOBYTE;
- utilities that modify device assignments;
- software expectations after reassignment.


Determine:

- what behavior applications can observe;
- what behavior applications reasonably depend upon.


2. LOGICAL DEVICE ASSIGNMENT

Determine the runtime semantics of logical devices.

Investigate:

- CON;
- RDR;
- PUN;
- LST.


Determine:

- how logical devices map to physical devices;
- how mappings change;
- how applications observe those changes.


3. DEVICE ASSIGNMENT STATE

Determine where device assignment state exists and how it changes.

Investigate:

- IOBYTE location;
- BDOS state;
- BIOS state;
- CCP interaction;
- persistence across operations.


Determine:

- whether state survives BDOS calls;
- whether state survives warm boot;
- whether state survives transient program execution.


4. STAT DEV AND DEVICE CONFIGURATION

Determine the compatibility behavior of device configuration tools.

Investigate:

- STAT DEV;
- device display;
- device assignment changes;
- reported state.


Determine:

- whether software depends upon STAT behavior;
- whether displayed information is compatibility-visible.


5. RUNTIME DEVICE SWITCHING

Determine behavior when devices are reassigned during execution.

Investigate:

- changing device mappings;
- active programs;
- CCP environment;
- BDOS operations.


Determine:

- whether applications observe changes immediately;
- whether state is cached;
- whether software depends upon a specific update model.


6. BDOS INTERACTION

Determine how BDOS character-device functions use device assignments.

Investigate:

- console functions;
- reader functions;
- punch functions;
- list functions.


Determine:

- whether BDOS always follows current assignment;
- whether exceptions exist;
- whether applications depend upon specific behavior.


7. BIOS INTERACTION

Determine how BIOS character services relate to IOBYTE.

Investigate:

- BIOS entry points;
- direct BIOS callers;
- device selection.


Determine:

- whether direct BIOS users bypass or depend upon IOBYTE;
- whether this is a compatibility concern.


8. SOFTWARE ECOSYSTEM USAGE

Investigate software that relies upon device reassignment.

Include categories:

- communications programs;
- terminal programs;
- printing utilities;
- file transfer utilities;
- development tools.


Determine:

- common usage patterns;
- undocumented assumptions;
- de facto compatibility requirements.


9. ERROR AND INVALID CONFIGURATION BEHAVIOR

Determine behavior when device assignments are invalid or unavailable.

Investigate:

- missing devices;
- unavailable hardware;
- invalid mappings;
- device failures.


Determine:

- application-visible behavior;
- required compatibility behavior.


10. SOURCE ANALYSIS

- IOBYTE handling;
