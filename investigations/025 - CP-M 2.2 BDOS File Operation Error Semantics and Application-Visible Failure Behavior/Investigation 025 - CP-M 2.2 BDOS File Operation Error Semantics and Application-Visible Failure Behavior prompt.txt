Application-Visible Failure Behavior

Continue the BetterCP/M CP/M 2.2 compatibility investigation series.

OBJECTIVE

Establish the application-visible CP/M 2.2 BDOS file-operation failure
contract.

Previous investigations established:

- FCB structure and CCP construction.
- Sequential and random read/write semantics.
- Directory allocation behavior.
- Allocation vectors and disk state.
- Transient lifecycle and termination.

Investigation 025 determines:

- what BDOS functions return on failure;
- which failures are distinguishable;
- which errors are application-visible;
- which conditions are implementation-dependent;
- which assumptions applications may safely make.

The goal is not to repeat file-operation mechanics.

The goal is to define the compatibility boundary around failure behavior.

SCOPE

Investigate application-visible behavior for:

- Open File failure;
- Make File failure;
- Close File failure;
- Delete File failure;
- Rename File failure;
- Search First failure;
- Search Next failure;
- Sequential Read failure;
- Sequential Write failure;
- Random Read failure;
- Random Write failure;
- disk-full conditions;
- directory-full conditions;
- read-only conditions;
- invalid drive conditions;
- malformed FCB conditions where safely testable.


NON-GOALS

Do not investigate:

- physical media failure beyond existing BIOS error handling;
- host filesystem behavior;
- CP/M 3 error extensions;
- compiler/runtime conventions;
- BetterCP/M implementation choices.

Do not infer requirements from a single DRI source behavior without
application-visible evidence.


KEY QUESTIONS


1. BDOS ERROR RETURN CONVENTIONS

Determine:

- normal success return values;
- failure return values;
- whether all failures are represented by FFh;
- functions with special return meanings.

Create a function/error matrix.


2. OPEN FAILURE

Determine behavior when:

- file does not exist;
- drive is invalid;
- user area differs;
- FCB contains wildcards;
- disk is unavailable.

Record:

- returned value;
- modified FCB state;
- directory state.


3. MAKE FAILURE

Determine behavior when:

- directory is full;
- disk allocation is exhausted;
- file already exists;
- invalid FCB supplied.

Determine whether partial allocation can occur.


4. CLOSE FAILURE

Determine:

- when Close can fail;
- whether failed Close leaves metadata modified;
- whether applications must retry;
- whether FCB state changes.


5. DELETE AND RENAME FAILURE

Determine:

- nonexistent file behavior;
- wildcard behavior;
- read-only behavior;
- invalid drive behavior;
- directory state afterward.


6. SEARCH FAILURE

Determine:

- Search First no-match behavior;
- Search Next exhaustion;
- FCB modifications;
- DMA contents after failure.

Cross-check directory search investigations.


7. READ FAILURES

Determine:

- EOF return;
- unallocated record behavior;
- invalid extent behavior;
- disk error behavior;
- DMA contents after failure.


8. WRITE FAILURES

Determine:

- disk-full behavior;
- directory-full behavior;
- allocation failure;
- partial-write behavior;
- FCB state after failure.


9. RANDOM ACCESS FAILURES

Determine:

- random record beyond EOF;
- invalid record values;
- file extension behavior;
- returned status.

Cross-check I013.


10. READ-ONLY BEHAVIOR

Determine how BDOS reports:

- read-only drive;
- read-only file behavior where applicable;
- attempted modification.

Do not confuse BDOS policy with BIOS write protection.


11. INVALID DRIVE BEHAVIOR

Determine:

- invalid drive selection;
- invalid FCB drive byte;
- current-drive interaction.

Cross-check I007.


12. FCB MODIFICATION ON FAILURE

Determine which FCB fields are:

- modified;
- preserved;
- undefined.

Especially:

- RC;
- EX;
- S1/S2;
- random record fields.


13. DMA CONTENT AFTER FAILURE

Determine whether failed operations:

- leave DMA unchanged;
- partially modify DMA;
- provide error information.

Do not assume.


14. DRI SOURCE ANALYSIS

Review BDOS source to determine:

- return paths;
- error checks;
- shared failure routines.

Do not produce source commentary.

Extract compatibility-relevant behavior only.

FINAL GOAL

Define the CP/M 2.2 BDOS file-operation failure contract:

When a CP/M application asks BDOS to perform a file operation and the
operation cannot succeed, exactly what does the application observe?

The result should distinguish:

- guaranteed compatibility behavior;
- DRI implementation behavior;
- undefined behavior;
- BetterCP/M policy choices.
