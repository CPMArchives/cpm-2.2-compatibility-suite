OBJECTIVE

Determine the compatibility assumptions made by common CP/M 2.2 software
beyond the documented operating-system interfaces.

Previous investigations established:

-   documented CP/M interfaces;
-   BDOS behavior;
-   BIOS behavior;
-   disk structure behavior;
-   direct system access behavior.

Investigation 042 determines which undocumented or de facto assumptions
were sufficiently widespread within the CP/M software ecosystem to
become compatibility requirements.

Investigate:

-   common application assumptions;
-   utility assumptions;
-   development tool assumptions;
-   software interaction patterns;
-   expectations about CP/M runtime behavior.

Determine:

-   which software assumptions are compatibility requirements;
-   which assumptions are implementation-specific;
-   which behaviors require further investigation.

COMPATIBILITY STANDARD

Consider:

-   documented CP/M 2.2 behavior;
-   Digital Research implementation behavior;
-   common CP/M programming practices;
-   historically significant software dependencies.

The objective is compatibility with the practical CP/M software
ecosystem, not only the published specification.

Do not assume undocumented behavior is required without evidence.

INVESTIGATION QUESTIONS

1.  SOFTWARE ECOSYSTEM CATEGORIES

Determine compatibility assumptions made by:

-   assemblers;
-   compilers;
-   editors;
-   database software;
-   communications programs;
-   disk utilities;
-   system utilities;
-   games and applications.

2.  COMMON RUNTIME ASSUMPTIONS

Determine whether software commonly assumes:

-   memory layout;
-   page-zero contents;
-   BDOS behavior;
-   BIOS availability;
-   CCP behavior;
-   disk organization;
-   device behavior.

3.  UNDOCUMENTED CONVENTIONS

Determine whether undocumented conventions became practical
compatibility requirements.

Investigate:

-   repeated use by independent software;
-   treatment as standard practice;
-   support by replacement systems;
-   reliance by widely used programs.

4.  SOFTWARE DEPENDENCY EVIDENCE

Determine how compatibility dependencies can be demonstrated.

Use evidence from:

-   source code;
-   documentation;
-   executable analysis;
-   reference-system testing;
-   historical usage.

5.  REPRESENTATIVE SOFTWARE TESTING

Create deterministic compatibility tests using representative software
where practical.

Record:

-   software tested;
-   CP/M behavior observed;
-   BetterCP/M implications;
-   compatibility conclusions.

6.  CONTROLLED TEST MATRIX

Include:

-   documented API usage;
-   common undocumented usage;
-   direct system access;
-   unusual but historically relevant usage;
-   failure cases where appropriate.
