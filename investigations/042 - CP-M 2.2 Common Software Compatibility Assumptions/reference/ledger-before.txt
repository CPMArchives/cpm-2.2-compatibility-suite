=============================== BETTERCP/M COMPATIBILITY LEDGER

  ---------
  PURPOSE
  ---------

This ledger records externally observable CP/M 2.2 behavior that
constrains a BetterCP/M implementation.

Each ledger entry represents one independently testable compatibility
proposition.

Disposition meanings:

REQUIRED BetterCP/M shall reproduce the behavior.

POLICY PENDING Evidence exists, but BetterCP/M has not yet adopted or
rejected the behavior as a compatibility requirement.

NOT REQUIRED BetterCP/M need not reproduce the behavior.

NOT GUARANTEED Portable CP/M software must not depend upon the behavior.

Detailed evidence, experiments, and unresolved questions remain in the
numbered investigation reports. The ledger records only the resulting
compatibility propositions and their current dispositions.

   001 - CP/M 2.2 Transient Program Entry Environment
  ----------------------------------------------------

1.  .COM load origin

    A transient .COM image is loaded beginning at 0100h.

    Disposition: REQUIRED

    Evidence: I001 sections 4-5; AG section 9; CCP; I024; I027; I028.

    Conformance: A test program’s first loaded byte appears at 0100h.

2.  Transient entry point

    Control is transferred to the transient program at 0100h.

    Disposition: REQUIRED

    Evidence: I001 sections 4-6; AG section 9; CCP CALL 0100h path;;
    I027; I028. ENTRY001 probe; I024.

    Conformance: A signature program begins execution at 0100h.

3.  TPA lower boundary

    The Transient Program Area begins at 0100h.

    Disposition: REQUIRED

    Evidence: I001 section 4; AG section 9; I024; I027; I028.

    Conformance: Memory below 0100h is not treated as ordinary transient
    program storage.

4.  TPA upper-bound discovery

    The operand of the jump at 0005h identifies the lowest resident CP/M
    address when the CCP is overlaid. The TPA extends up to, but not
    including, that configured boundary.

    The exact numeric boundary is configuration-dependent.

    Disposition: REQUIRED

    Evidence: I001 sections 4-5; AG section 9; I024; I027; I028.

    Conformance: LHLD 0006h yields the advertised low resident boundary.

5.  Warm-start gateway at 0000h

    Locations 0000h-0002h contain a jump to the BIOS warm-start entry.
    Transferring control to 0000h invokes programmed warm restart
    behavior.

    Disposition: REQUIRED

    Evidence: I001 sections 4 and 11; AG section 9; I020; I027; I028.
    WBOOT20/PZERO20.

    Conformance: JMP 0000h performs warm-start semantics.

6.  IOBYTE location

    Location 0003h is the Intel-standard IOBYTE when implemented by the
    target CBIOS.

    The IOBYTE itself is optional as permitted by the CP/M 2.2 BIOS
    environment.

    Disposition: REQUIRED

    Evidence: I001 section 4; AG section 9; I027; I028.

    Conformance: Where implemented, 0003h has the documented IOBYTE
    meaning.

7.  Command-entry default-drive byte

    Location 0004h contains the command-environment default-drive code
    supplied at transient entry:

    0 = A: … 15 = P:

    The byte reflects CCP command-entry/warm-start state. It is not a
    guaranteed live BDOS current-drive query after transient execution
    changes drive state. Portable software must use BDOS function 25 to
    query live current-disk state after BDOS drive-selection operations.

    Disposition: REQUIRED

    Evidence: I001 section 4; AG section 9; I007 analysis of DRI CCP;
    I027; I028. and BDOS drive-state handling.

    Conformance: At transient entry, 0004h contains the command
    environment drive. Function 25 is used to test live BDOS current
    drive state.

8.  BDOS gateway at 0005h

    Locations 0005h-0007h contain the jump to BDOS and form the primary
    CP/M system-service gateway.

    Disposition: REQUIRED

    Evidence: I001 sections 4 and 11; AG section 9; I020; I027; I028.
    WBOOT20/PZERO20.

    Conformance: CALL 0005h invokes BDOS and returning services resume
    after the call.

9.  Reserved restart/interrupt region roles

    Locations 0008h-003Ah retain the documented CP/M 2.2 restart and
    interrupt-location roles.

    No fixed contents are required where CP/M documentation leaves
    locations unused or reserved.

    Disposition: REQUIRED

    Evidence: I001 section 4; AG section 9; I027; I028.

    Conformance: BetterCP/M does not assign incompatible baseline
    meanings to documented restart/interrupt locations.

10. CBIOS scratch-area role

    Locations 0040h-004Fh retain the documented 16-byte CBIOS
    scratch-area role in the distribution arrangement.

    The exact contents are not a general compatibility guarantee.

    Disposition: REQUIRED

    Evidence: I001 section 4; AG section 9; I024; I027; I028.

    Conformance: Software is not promised fixed contents in this area.

11. First default FCB location

    The CCP supplies the first default unopened File Control Block
    beginning at 005Ch.

    Disposition: REQUIRED

    Evidence: I001 sections 4 and 11; AG section 9; CCP; I027; I028.

    Conformance: A transient with a first file operand finds its default
    FCB beginning at 005Ch.

12. Second default FCB at 006Ch

    The DRI CCP supplies a second unopened default FCB beginning at
    006Ch for the second operand.

    This overlaps the allocation area of the first default FCB.

    Investigation 001 established the behavior from DRI source and
    experiment but did not establish it as an explicit documented CP/M
    2.2 requirement.

    Disposition: POLICY PENDING

    Evidence: I001 sections 4-6, 8 and 11; CCP; ENTRY001 probe; I021;
    I027; I028.

    Conformance: Diagnose separately from first-FCB behavior until
    policy or stronger documentary/software-dependency evidence resolves
    the disposition.

13. Default FCB drive-prefix parsing

    The DRI CCP interprets a drive prefix in a command operand and
    places the corresponding drive code into the default FCB.

    Disposition: REQUIRED

    Evidence: I001 sections 4-6 and 8; CCP fillfcb behavior; ENTRY001;
    I027; I028. probe; I021; Features and Facilities section 2.2; CCP;
    PARSE21.

    Conformance: Test independently with explicit drive prefixes.

14. Default FCB wildcard expansion

    The DRI CCP expands ’*’ through the remaining filename/type field as
    ‘?’ characters when constructing a default FCB.

    Disposition: REQUIRED

    Evidence: I001 sections 4-5 and 8; CCP fillfcb implementation;;
    I027; I028. I021; documented * abbreviation; CCP; PARSE21.

    Conformance: Test ’*’ and ‘?’ cases independently.

15. Default FCB case and padding

    The DRI CCP constructs default FCB filename/type fields in uppercase
    and pads unused characters with spaces.

    Disposition: REQUIRED

    Evidence: I001 sections 4-6 and 8; CCP; ENTRY001 probe; I021;; I027;
    I028. documented lowercase translation/FCB form; CCP; PARSE21.

    Conformance: Compare resulting filename/type bytes for
    representative operands.

16. Default FCB unopened control fields

    The DRI CCP initializes the extent-related and other unopened-FCB
    control fields as described in Investigation 001.

    Disposition: POLICY PENDING

    Evidence: I001 sections 4-6 and 8; CCP fillfcb implementation;;
    I027; I028. I021.

    Conformance: Test the initialized fields separately from filename
    parsing.

17. Command-tail count location

    Byte 0080h contains the command-tail character count at transient
    entry.

    Disposition: REQUIRED

    Evidence: I001 section 4; AG section 9; I027; I028.

    Conformance: 0080h contains the count for the supplied command tail.

18. Command-tail character location

    Command-tail characters begin at 0081h.

    Disposition: REQUIRED

    Evidence: I001 section 4; AG section 9; I027; I028.

    Conformance: The counted command characters occupy the documented
    buffer.

19. Leading blank in command tail

    The DRI CCP includes the separating blank preceding the first
    command argument as the first counted command-tail character.

    Disposition: POLICY PENDING

    Evidence: I001 sections 4-6 and 8; CCP command reader; ENTRY001;
    I027; I028. probe; I021.

    Conformance: Test independently from case conversion and
    termination.

20. Uppercase command-tail representation

    The DRI CCP supplies the command tail in uppercase.

    Disposition: POLICY PENDING

    Evidence: I001 sections 4-6 and 8; CCP command-reader behavior;;
    I027; I028. ENTRY001 probe; I021.

    Conformance: Test mixed-case command input where the reference
    environment permits it.

21. NUL after counted command tail

    The DRI CCP writes a zero byte immediately after the counted
    command-tail characters. The terminating zero is not included in the
    count at 0080h.

    Disposition: POLICY PENDING

    Evidence: I001 sections 4-6 and 8; CCP; ENTRY001 probe; I021; I027;
    I028.

    Conformance: Verify the byte immediately following the counted tail
    independently from the tail count itself.

22. Bytes following command-tail terminator

    DRI CP/M may leave stale prior buffer contents after the zero
    following the command tail.

    BetterCP/M need not reproduce those stale bytes.

    Disposition: NOT REQUIRED

    Evidence: I001 sections 6-9 and 11; ENTRY001 observation; I027;
    I028.

    Conformance: Tests may report these bytes diagnostically but must
    not require a particular value.

23. Default DMA address

    The default DMA address at transient entry is 0080h.

    Disposition: REQUIRED

    Evidence: I001 sections 4-5 and 11; AG; CCP set-DMA path; I026;
    I027; I028; I030.

    Conformance: The first disk operation using the unchanged default
    DMA operates on 0080h.

24. Command-tail/default-DMA overlap

    At transient entry the command tail occupies the same 0080h-00FFh
    buffer that serves as the default DMA area.

    Disposition: REQUIRED

    Evidence: I001 section 4; AG; CCP behavior; I026; I027; I028; I030.

    Conformance: Initial contents of the default DMA buffer are the
    command tail, not an implied disk record.

25. Program termination through JMP 0000h

    A transient program may terminate by transferring control to 0000h,
    invoking the warm-start path.

    Disposition: REQUIRED

    Evidence: I001 sections 4 and 11; AG section 9; I024; I027; I028.

    Conformance: JMP 0000h regains the command environment with
    warm-start semantics.

26. Program termination through BDOS function 0

    BDOS function 0 terminates the transient through the system
    warm-start path.

    Disposition: REQUIRED

    Evidence: I001 sections 4 and 11; BDOS function table; I024; I027;
    I028.

    Conformance: Function 0 regains the command environment with
    warm-start semantics.

27. RET termination

    A transient program may terminate with RET.

    Investigation 002 supplied the stronger documentary evidence missing
    from Investigation 001 and upgrades this behavior from
    policy-pending to REQUIRED.

    Disposition: REQUIRED

    Evidence: I001 sections 5-6 and 8-11; I002 documented CCP; I027;
    I028. stack/RET finding; I024.

    Conformance: A minimal transient containing RET returns safely to
    the command environment without requiring BIOS warm start.

28. Valid entry return word

    At transient entry SP addresses a valid return word suitable for
    ordinary RET termination.

    The existence and function of the return word are required; its
    exact numeric value is not.

    Disposition: REQUIRED

    Evidence: I001 sections 5-6; ENTRY001 stack snapshot; I002; I027;
    I028. documentary correction; I024.

    Conformance: RET from entry succeeds using the supplied return word.

29. Exact entry SP

    BetterCP/M need not reproduce DRI’s numeric transient-entry SP.

    Disposition: NOT REQUIRED

    Evidence: I001 sections 6-9; I002 correction; I024; I027; I028.

    Conformance: Software may rely on a usable return stack but not on a
    particular SP value.

30. Exact entry return address

    BetterCP/M need not reproduce the numeric DRI CCP return address
    stored at transient entry.

    Disposition: NOT REQUIRED

    Evidence: I001 sections 6-9; I002 correction; I024; I027; I028.

    Conformance: The return word must function correctly but need not
    point to the same numeric address or CCP routine as DRI CP/M.

31. General-register entry state

    No particular initial value is guaranteed for AF, BC, DE, or HL
    except where another compatibility proposition explicitly defines an
    input.

    Disposition: NOT GUARANTEED

    Evidence: I001 sections 5-9 and 11; I027; I028.

    Conformance: BetterCP/M may expose different residual values.

32. Z80 extended-register entry state

    No particular initial value is guaranteed for IX, IY, alternate
    register pairs, I, or R.

    Disposition: NOT GUARANTEED

    Evidence: I001 sections 5-9 and 11; I027; I028.

    Conformance: BetterCP/M may expose different residual values.

33. Entry flags and interrupt state

    No particular initial flags or interrupt-enable state are guaranteed
    by the investigated CP/M 2.2 transient-entry contract.

    Disposition: NOT GUARANTEED

    Evidence: I001 sections 5-9 and 11; I027; I028.

    Conformance: Programs must not rely upon the reference system’s
    observed values.

34. Exact BIOS/BDOS vector targets

    The warm-start and BDOS gateways must have the required semantics,
    but the numeric target addresses of their page-zero jumps are
    configuration-specific and need not match DRI/z80pack values.

    Disposition: NOT REQUIRED

    Evidence: I001 sections 6-7 and 11; I027; I028.

    Conformance: Test the gateway semantics, not particular target
    addresses.

  ------------------------------------------------
   002 - CP:M 2.2 BDOS Call and Return Convention
  ------------------------------------------------

35. BDOS function selector in C

    C contains the BDOS function selector when the service gateway is
    entered.

    Disposition: REQUIRED

    Evidence: I002 documented call convention; DRI Interface Guide and
    BDOS source.

    Conformance: Every implemented BDOS function interprets C as the
    selector.

36. BDOS function-specific input in DE/E

    Function-specific information is supplied in DE, or in E for
    byte-valued parameters where the selected function defines that
    convention.

    DE must not be described generically as always containing a pointer.

    Disposition: REQUIRED

    Evidence: I002 documented call convention and per-function
    definitions.

    Conformance: Representative functions correctly consume their
    documented DE/E input.

37. Byte result in A

    A BDOS function returning a one-byte result returns that result in

    A.  

    Disposition: REQUIRED

    Evidence: I002 section 4; DRI Interface Guide; ABI002 probe.

    Conformance: Byte-returning functions are checked independently in

    A.  

38. Word result in HL

    A BDOS function returning a two-byte result returns that result in
    HL.

    Disposition: REQUIRED

    Evidence: I002 section 4; DRI Interface Guide; ABI002 probe.

    Conformance: Word-returning functions are checked independently in
    HL.

39. Normal-return alias A=L

    Every normally returning BDOS call establishes A equal to L.

    Disposition: REQUIRED

    Evidence: I002 documented convention; DRI BDOS common epilogue;
    ABI002 probe.

    Conformance: Assert A=L on every returning baseline function,
    including error returns.

40. Normal-return alias B=H

    Every normally returning BDOS call establishes B equal to H.

    Disposition: REQUIRED

    Evidence: I002 documented convention; DRI BDOS common epilogue;
    ABI002 probe.

    Conformance: Assert B=H on every returning baseline function.

41. CP/M 2.2 BDOS selector range

    CP/M 2.2 implements function selectors 0 through 40 inclusive.

    Disposition: REQUIRED

    Evidence: I002; DRI CP/M 2.2 BDOS 41-entry dispatch table.

    Conformance: Baseline functions 0-40 are accounted for individually.

42. Out-of-range BDOS result

    In strict CP/M 2.2 behavior, function selectors outside 0-40 return
    a zero result.

    With the normal result aliases this yields:

    HL = 0000h A = 00h B = 00h

    Disposition: REQUIRED

    Evidence: I002 documented out-of-range rule; DRI BDOS dispatch;
    ABI002 function-41 probe.

    Conformance: Test representative selectors including 41, 42, 7Fh,
    80h, and FFh.

43. Caller SP restored on returning BDOS calls

    A BDOS function that returns restores the caller’s SP before control
    returns to the caller.

    Disposition: REQUIRED

    Evidence: I002 documented stack convention; DRI BDOS stack handling;
    ABI002 probe.

    Conformance: Verify pre-call and post-return SP are equal for
    returning functions.

44. DRI private BDOS stack mechanism

    BetterCP/M need not reproduce DRI’s particular private local-stack
    implementation.

    Only the externally visible balanced-call behavior is required.

    Disposition: NOT REQUIRED

    Evidence: I002 stack analysis.

    Conformance: Do not test DRI internal stack addresses or
    implementation.

45. AF preservation across BDOS

    BDOS provides no general preservation guarantee for AF beyond
    explicitly defined return values.

    Disposition: NOT GUARANTEED

    Evidence: I002 documentation analysis and probe.

    Conformance: Callers must treat unspecified AF/flags state as
    clobbered.

46. BC preservation across BDOS

    BDOS provides no general preservation guarantee for BC.

    B is explicitly part of the normal result alias and therefore may
    change.

    Disposition: NOT GUARANTEED

    Evidence: I002 documentation and implementation analysis.

    Conformance: Callers must not depend upon BC preservation.

47. DE preservation across BDOS

    BDOS provides no general preservation guarantee for DE.

    ABI002 demonstrated handler-dependent DE clobbering.

    Disposition: NOT GUARANTEED

    Evidence: I002; ABI002 function 26 observation.

    Conformance: Callers must not depend upon DE preservation.

48. HL preservation across BDOS

    BDOS provides no general preservation guarantee for HL.

    HL is the documented word-result register pair.

    Disposition: NOT GUARANTEED

    Evidence: I002 documented result convention.

    Conformance: Callers must not depend upon prior HL surviving a call.

49. Z80-only and alternate-register preservation

    CP/M 2.2 provides no documented general preservation guarantee for
    IX, IY, alternate register pairs, I, or R across BDOS.

    Their survival in the tested reference calls is not a portable
    requirement.

    Disposition: NOT GUARANTEED

    Evidence: I002 source/probe analysis.

    Conformance: Diagnostic tests may report changes but must not fail
    because BetterCP/M clobbers these registers.

50. Valid-call C becomes input E

    DRI CP/M 2.2’s dispatcher copies input E into C on valid calls.

    This is undocumented dispatcher residue and is not a BetterCP/M
    compatibility requirement.

    Disposition: NOT REQUIRED

    Evidence: I002 DRI source analysis and ABI002 observations.

    Conformance: Applications must not rely upon returned C mirroring
    the input E value.

51. Observed BDOS return flags

    Particular flags observed after DRI BDOS returns are implementation
    residue unless an individual function explicitly defines flag
    semantics.

    Disposition: NOT REQUIRED

    Evidence: I002 source/probe observations.

    Conformance: Generic BDOS tests do not require the DRI reference
    flags.

   003 - CP:M 2.2 BDOS Console Output and String Output Semantics

52. Function 2 character source

    BDOS function 2 outputs the character supplied in E.

    Disposition: REQUIRED

    Evidence: I003; DRI Interface Guide; DRI BDOS source; OUT003 probe.

    Conformance: Representative byte values supplied in E are emitted
    through the formatted console-output path.

53. Function 2 treats ‘$’ as ordinary data

    BDOS function 2 gives ‘′nospecialterminatormeaning.A′’ supplied in E
    is output as a character.

    Disposition: REQUIRED

    Evidence: I003; OUT003 probe.

    Conformance: Function 2 with E=‘′emits′’.

54. Function 9 string address

    BDOS function 9 begins scanning the output string at the address
    supplied in DE.

    Disposition: REQUIRED

    Evidence: I003; DRI Interface Guide; DRI BDOS source; OUT003 probe.

    Conformance: Output begins with the byte at the supplied DE address.

55. Function 9 ‘$’ termination

    BDOS function 9 stops scanning at the first ‘$’ byte.

    Disposition: REQUIRED

    Evidence: I003; DRI Interface Guide; DRI BDOS source; OUT003 probe.

    Conformance: Bytes following the first ‘$’ are not emitted by that
    call.

56. Function 9 terminator is not emitted

    The ‘$’ byte that terminates a function 9 string is not itself
    output.

    Disposition: REQUIRED

    Evidence: I003; DRI Interface Guide; OUT003 probe.

    Conformance: The terminating ‘$’ does not appear in the console
    stream.

57. Function 9 empty string

    If the first byte addressed by DE is ‘$’, BDOS function 9 emits no
    string characters.

    Disposition: REQUIRED

    Evidence: I003; OUT003 probe.

    Conformance: A string beginning with ‘$’ produces empty output.

58. Function 9 scans across ordinary control characters

    Characters such as CR and LF occurring before the terminating ‘$’
    are processed as string characters and do not terminate function 9
    scanning.

    Disposition: REQUIRED

    Evidence: I003; OUT003 probe.

    Conformance: A function 9 string containing embedded CR/LF continues
    until the first ‘$’.

59. Function 2 uses formatted console output

    BDOS function 2 is a formatted logical-console service rather than a
    raw physical-console byte output operation.

    Disposition: REQUIRED

    Evidence: I003; DRI Interface Guide; DRI BDOS source; OUT003 probe.

    Conformance: Function 2 participates in the documented
    formatted-output behaviors tested separately below.

60. Function 9 uses formatted console output

    Characters emitted by BDOS function 9 pass through the same
    formatted logical-console processing used by function 2.

    Disposition: REQUIRED

    Evidence: I003; DRI BDOS source; OUT003 probe.

    Conformance: Function 9 participates in the same formatted-output
    state and transformations as function 2.

61. Shared formatted-output state

    BDOS functions 2 and 9 share persistent formatted-console state
    across calls.

    Disposition: REQUIRED

    Evidence: I003; DRI BDOS source; OUT003 probe.

    Conformance: Output by one function affects subsequent formatting by
    the other where the formatting rule depends on prior output state.

62. TAB expansion

    In formatted console output, TAB advances to the next eight-column
    tab stop by emitting spaces.

    Disposition: REQUIRED

    Evidence: I003; DRI BDOS source; OUT003 probe.

    Conformance: TABs at known logical columns expand to the required
    number of spaces to reach the next eight-column stop.

63. Function 2 participates in scrolling control

    BDOS function 2 participates in CP/M’s formatted-console scrolling
    control behavior.

    Disposition: REQUIRED

    Evidence: I003; DRI documentation and BDOS source.

    Conformance: A deterministic keyboard-input harness should verify
    the documented scrolling-control behavior.

64. Function 9 participates in scrolling control

    Characters emitted by BDOS function 9 participate in the same
    formatted-console scrolling control behavior.

    Disposition: REQUIRED

    Evidence: I003; DRI documentation and BDOS source.

    Conformance: A deterministic keyboard-input harness should verify
    the documented scrolling-control behavior during function 9.

65. Function 2 participates in active printer echo

    When CP/M printer echo is active, characters emitted through BDOS
    function 2 are also sent through the logical printer path after
    formatted-console processing.

    Disposition: REQUIRED

    Evidence: I003; DRI documentation and BDOS source; printer-echo
    experiment.

    Conformance: With printer echo enabled, function-2 output appears at
    the logical printer as well as the console.

66. Function 9 participates in active printer echo

    When CP/M printer echo is active, characters emitted by BDOS
    function 9 are also sent through the logical printer path after
    formatted-console processing.

    Disposition: REQUIRED

    Evidence: I003; DRI documentation and BDOS source; printer-echo
    experiment.

    Conformance: With printer echo enabled, function-9 output appears at
    the logical printer as well as the console.

67. Function 2 has no function-specific return value

    CP/M 2.2 defines no function-specific return value for BDOS function

    2.  

    The general BDOS return convention established by Investigation 002
    still applies.

    Disposition: NOT GUARANTEED

    Evidence: I003; DRI Interface Guide; I002.

    Conformance: Tests must not require a function-2-specific result
    value.

68. Function 9 has no function-specific return value

    CP/M 2.2 defines no function-specific return value for BDOS function

    9.  

    The general BDOS return convention established by Investigation 002
    still applies.

    Disposition: NOT GUARANTEED

    Evidence: I003; DRI Interface Guide; I002.

    Conformance: Tests must not require a function-9-specific result
    value.

69. Exact logical-column update rules

    DRI CP/M maintains a logical output column for formatted console
    processing, but some exact character-by-character update rules are
    implementation behavior not yet established as portable CP/M 2.2
    requirements.

    Disposition: POLICY PENDING

    Evidence: I003; DRI BDOS source.

    Conformance: Keep exact column-update rules diagnostic until later
    evidence or policy resolves them.

70. LF resets DRI logical column

    DRI CP/M resets its logical output column on LF.

    Investigation 003 did not establish this exact DRI rule as a
    portable CP/M 2.2 requirement.

    Disposition: POLICY PENDING

    Evidence: I003; DRI BDOS source.

    Conformance: Diagnose independently from required TAB-stop behavior.

71. CR does not reset DRI logical column

    DRI CP/M does not reset its internal logical output column merely
    because CR is emitted.

    Investigation 003 did not establish this exact DRI rule as a
    portable CP/M 2.2 requirement.

    Disposition: POLICY PENDING

    Evidence: I003; DRI BDOS source.

    Conformance: Diagnose independently from required output of the CR
    byte.

     beginning at 005Ch. The DRI CP/M 2.2 CCP represents the second

     Whether every BetterCP/M-compatible CCP must provide this second
     prefix remains unresolved.

     CCP preparation does not guarantee zero or any other fixed value in
     default-FCB bytes outside the constructed drive/name/type/EX/S1/S2

     Disposition: NOT GUARANTEED

     Evidence: I023; CCP; IG; I028.

     Conformance: A compatible implementation may vary residual bytes
     without failing compatibility.

     The command tail delivered by the DRI CCP is the suffix of its

     count depends on command-token length. The exact
     cross-implementation minimum capacity is not established.

     Disposition: POLICY PENDING

     Evidence: I023; I021; I024; CCP; I028.

     Conformance: Boundary tests must distinguish accepted CCP

   024 - CP-M 2.2 Transient Program Lifecycle, Termination, and BDOS Return-
                                State Semantics
  ---------------------------------------------------------------------------

509. Transient termination mechanisms

     A CP/M 2.2 transient can return control through the valid entry RET
     environment, invoke BDOS Function 0 (System Reset), or branch to
     0000h. RET returns through CCP without WBOOT; Function 0 and 0000h
     invoke warm-start semantics. All must restore a usable CCP
     environment.

     Disposition: REQUIRED

     Evidence: I024; I002; I022; CCP; BDOS; AG; I026; I027; I028; I030;
     I035.

     Conformance: Execute minimal transients using each mechanism and
     verify a usable CCP prompt, distinguishing RET from WBOOT by
     controlled page-zero reconstruction.

510. RET does not generally reconstruct page zero

     Normal RET termination follows CCP’s post-call path and need not
     restore arbitrary application modifications to page zero. Required
     semantic gateways must remain usable when the application obeys the
     entry contract, but no general RET-time memory cleanup is
     guaranteed.

     Disposition: NOT GUARANTEED

     Evidence: I024; CCP; I026; I027; I028; I030; I035.

     Conformance: Install safe forwarding modifications to 0000h/0005h,
     terminate by RET, and verify that compatibility does not depend on
     CCP rewriting them.

511. Termination does not implicitly close application FCBs

     RET, BDOS Function 0, and JMP 0000h do not guarantee an implicit
     Close or file-length finalization for FCB writes. Applications must
     explicitly close files when Close is required to persist metadata.

     Disposition: NOT GUARANTEED

     Evidence: I024; CCP; BDOS; IG; I026; I027; I028; I030.

     Conformance: Make and write a record without Close, terminate
     through each path, and verify that an implementation is not
     required to finalize the FCB as if Function 16 had been called.

512. Post-termination drive and user policy

     The DRI RET path restores CCP’s saved command drive while leaving
     the selected BDOS user active; the tested WBOOT paths preserved
     coherent selected drive/user state. The exact portable preservation
     rule across BIOS implementations is not fully established beyond
     documented WBOOT drive handoff semantics.

     Disposition: POLICY PENDING

     Evidence: I024; I007; CCP; AG; I026; I027; I028; I030; I035.

     Conformance: Change drive and user, terminate through all three
     mechanisms, and measure the next CCP prompt and BDOS Functions
     25/32 without assuming DRI’s private state arrangement.

  ----------------------------------------------------------------------------

513. File-operation failures are function-specific

     CP/M 2.2 does not define one universal BDOS file-operation error
     value. Applications must interpret BDOS results according to the
     selected function.

     Disposition: REQUIRED

     Evidence: I025; IG; BDOS; I008-I013; I027; I029; I030.

514. Failure does not generally validate DMA contents

     A failed file operation does not generally guarantee valid DMA
     contents or preservation of DMA contents.

     Disposition: NOT GUARANTEED

     Evidence: I025; I009; I010; I013; BDOS; I027; I029; I030.

515. FCB state after precondition or operation failure

     CP/M 2.2 does not guarantee an exact FCB byte state after failed
     operations, especially for malformed or unactivated FCBs.

     Disposition: NOT GUARANTEED

     Evidence: I025; I008; I010-I013; BDOS; I027; I029; I030.

516. Directory-full and allocation-full are distinct

     CP/M 2.2 distinguishes exhaustion of directory entries from
     exhaustion of allocation blocks. Make and Write failures may
     therefore occur at different stages.

     Disposition: REQUIRED

     Evidence: I025; I011; IG; BDOS; I027; I029; I030.

517. Malformed FCB behavior is outside the portable contract

     Invalid drive encodings, unactivated FCB use, and caller-corrupted
     FCB contents do not define a portable CP/M 2.2 return or mutation
     contract.

     Disposition: NOT GUARANTEED

     Evidence: I025; I008; I010-I013; IG; I027; I029; I030.

  --------------------------------------------------------------------------
   026 - CP/M 2.2 BDOS System State Functions and Application-Visible Envi-
                              ronment Semantics
  --------------------------------------------------------------------------

518. BDOS system state components

     BDOS maintains distinct application-visible system state components
     including current drive, login state, read-only state, user code,
     and DMA address. These components have separate query and mutation
     semantics.

     Disposition: REQUIRED

     Evidence: I026; BDOS; IG; I007; I014; I017; I027; I028; I029; I030;
     I031.

     Conformance: Change and query each state component independently.

519. BIOS-owned selected-drive resources

     BIOS selection supplies drive-specific DPH/DPB/ALV resources while
     BDOS owns application-visible selection, login, protection, and DMA
     policy.

     Disposition: REQUIRED

     Evidence: I026; BDOS; AG; I017; I019; I027; I028; I029; I030; I031.

     Conformance: Select drives and verify BDOS exposes the
     corresponding BIOS resources without requiring a particular
     address.

520. Function 26 persistence boundary

     A Function-26 DMA address remains selected for subsequent disk
     transfers until another Function 26, disk-system reset, warm start,
     or cold start.

     Disposition: REQUIRED

     Evidence: I026; IG; BDOS; I009; I024; I027; I028; I029; I030; I031.

     Conformance: Interpose nonresetting BDOS calls before a transfer,
     then test each documented reset boundary.

521. System-state independence

     Current drive, login membership, read-only membership, user code,
     and DMA address are distinct state; changing one does not imply
     undocumented synchronization of all others.

     Disposition: REQUIRED

     Evidence: I026; BDOS; I007; I017; I027; I028; I029; I030; I031.

     Conformance: Alter each component and query the others.

522. ALV and DPB pointer lifetime

     Exact Function-27/31 pointer values and continued validity after
     disk selection, reset, relogin, or boot transitions are not
     portable.

     Disposition: NOT GUARANTEED

     Evidence: I026; IG; AG; I017; I019; I027; I028; I029; I030; I031.

     Conformance: Applications re-query after state transitions;
     conformance does not compare DRI numeric addresses.

523. Function 37 compatibility status

     DRI CP/M 2.2 Function 37 clears DE-selected bits from both login
     and read-only vectors without changing the current-drive number,
     but the examined application manuals do not document the service.

     Disposition: POLICY PENDING

     Evidence: I026; BDOS; I007; I017; IG/AG silence; I027; I028; I029;
     I030; I031.

     Conformance: If adopted, test inactive, current, multiple, and
     read-only drive bits independently.

524. CP/M 2.2 Function 39 has no Get-BIOS contract

     CP/M 2.2 does not define Function 39 as Get BIOS; DRI’s observed
     zero is an implementation result and does not expose a BIOS
     address.

     Disposition: NOT REQUIRED

     Evidence: I026; BDOS; IG; AG; I027; I028; I029; I030; I031.

     Conformance: Do not require a Get-BIOS pointer from selector 39.

525. CP/M 2.2 selectors 40 and 41

     Function 40 is Random Write with Zero Fill. Function 41 file
     attributes are outside CP/M 2.2, whose implemented selector range
     ends at 40.

     Disposition: REQUIRED

     Evidence: I026; AG; BDOS; I002; I013; I027; I028; I029; I030; I031.

     Conformance: Test Function 40 as random write; require no
     Function-41 extension for CP/M 2.2 conformance.

  ----------------------------------------------------------------------------
    027 - CP/M 2.2 BDOS Call Interface Convention and Register-State Semantics
  ----------------------------------------------------------------------------

526. Common BDOS gateway and invocation

     Returning BDOS services are invoked by CALL 0005h through the
     page-zero BDOS jump; applications must not depend on its private
     destination.

     Disposition: REQUIRED

     Evidence: I027; IG; AG; BDOS; I001; I002; I028.

     Conformance: Relocate the BDOS target while preserving the 0005h
     gateway.

527. Common selector and parameter carriers

     C carries the selector and DE/E carries function-specific input;
     unused registers need not contain defined values.

     Disposition: REQUIRED

     Evidence: I027; IG; BDOS; I002; I028.

     Conformance: Exercise pointer, word, byte, and unused DE/E cases.

528. Common result and alias convention

     Normal returns place byte results in A and word results in HL, with
     A=L and B=H in all cases.

     Disposition: REQUIRED

     Evidence: I027; IG; BDOS; I002; CALL27; FUNC27; I028.

     Conformance: Check primary and alias registers for success, error,
     void, and out-of-range returns.

529. Strict CP/M 2.2 unsupported selectors

     Selectors 41-255 are outside CP/M 2.2’s 0-40 table and return zero
     with HL=0000h, A=L=00h, and B=H=00h.

     Disposition: REQUIRED

     Evidence: I027; IG; BDOS; I002; FUNC27; I028.

     Conformance: Test 41, 42, 7Fh, 80h, and FFh in strict mode.

530. General register preservation

     No general preservation is guaranteed for registers or flags beyond
     function-defined outputs, result aliases, and restored caller SP.

     Disposition: NOT GUARANTEED

     Evidence: I027; IG silence; BDOS; I002; REG27; I028.

     Conformance: Applications reload needed inputs and tests accept
     arbitrary undocumented residual register state.

531. Returning-call stack balance

     A normally returning BDOS call restores the caller’s SP and
     consumes no caller-owned stack beyond the ordinary call/return
     requirement.

     Disposition: REQUIRED

     Evidence: I027; IG; BDOS; I002; STACK27; I028.

     Conformance: Repeat returning calls on a guarded caller stack and
     compare SP.

532. Invalid parameters are function-specific

     The common BDOS ABI defines no universal result or safe behavior
     for invalid drives, pointers, malformed FCBs, or violated
     preconditions.

     Disposition: NOT GUARANTEED

     Evidence: I027; I025; BDOS; IG function-specific contracts; I028;
     I030.

     Conformance: Validate documented errors per function and require no
     common bad-parameter code.

533. BDOS reentrancy

     CP/M 2.2 does not guarantee recursive, nested, or interrupt-time
     BDOS entry while a prior call is active.

     Disposition: NOT GUARANTEED

     Evidence: I027; IG silence; DRI global-state/local-stack; I028.
     structure.

     Conformance: Compatible applications do not make nested calls; no
     DRI private implementation is required.

  --------------------------------------------------------------------------
   028 - CP/M 2.2 CCP Transient Execution Handoff and Loader State Contract
  --------------------------------------------------------------------------

534. Complete transient handoff

     Before execution at 0100h, CCP provides the required page-zero
     gateways, command environment, default FCB/tail state, default DMA,
     and RET context.

     Disposition: REQUIRED

     Evidence: I028; CCP; AG; IG; I022; I023; I027; I029.

     Conformance: Capture all public entry objects before the first
     diagnostic call and immediately invoke BDOS.

535. Handoff preparation ordering

     CP/M 2.2 does not require an exact internal ordering for load,
     page-zero, FCB, tail, DMA, or private CCP preparation when the
     complete entry state is established before control reaches 0100h.

     Disposition: NOT REQUIRED

     Evidence: I028; CCP; documentation specifies resulting interfaces;
     I029.

     Conformance: Test entry state, not private instruction order.

536. Unloaded transient memory

     Memory above the accepted COM records, unused TPA space, and any
     separate stack area have no defined initial contents and need not
     be cleared or preserved between transient programs.

     Disposition: NOT GUARANTEED

     Evidence: I028; IG/AG silence; CCP; MEM28 residue experiment; I029.

     Conformance: Vary unused memory contents; applications initialize
     storage before relying on it.

537. Immediate BDOS readiness

     The page-zero BDOS gateway and initialized BDOS state are usable by
     the transient immediately upon entry at 0100h.

     Disposition: REQUIRED

     Evidence: I028; AG; IG; CCP; I027; LOAD28/ENTRY28; I029.

     Conformance: Make a documented BDOS call as the first external
     operation.

538. Loader DMA isolation

     CCP’s changing DMA destinations used to load COM records are not
     inherited; the transient entry DMA is restored to 0080h with the
     command buffer.

     Disposition: REQUIRED

     Evidence: I028; CCP; I022; I023; AG; I029; I035.

     Conformance: Load a multirecord program and use DMA immediately
     without Function 26.

539. Transient stack preparation

     CCP supplies a valid CALL-produced RET word, but no exact entry SP,
     return address, deeper stack contents, or separately cleared
     application stack.

     Disposition: NOT GUARANTEED

     Evidence: I028; IG; CCP; I001; I023; I027; I029.

     Conformance: Require immediate RET to work while varying numeric
     stack state.

540. Load rejection suppresses execution

     Missing, failed, or oversized transient loads do not execute
     partial/rejected bytes and recover a usable command environment at
     the applicable error layer.

     Disposition: REQUIRED

     Evidence: I028; CCP; I022; I025; ERROR28/BIGERR28; I029; I030.

     Conformance: Embed a visible entry marker and verify it is absent
     on failure.

541. Post-RET reconstruction boundary

     After ordinary RET, CCP may reconstruct command drive/user, stack,
     DMA, and page-zero state needed for the next command; arbitrary TPA
     residue and transient-selected state are not a persistence
     interface.

     Disposition: NOT GUARANTEED

     Evidence: I028; CCP; I024; I026; RETURN28/CHECK28; I029; I030;
     I035.

     Conformance: Mutate state and memory, return, and validate only the
     next command’s documented environment.

  ------------------------------------------------------------------------
   029 - CP/M 2.2 BDOS Directory Search Semantics and FCB/DMA Enumeration
                                  Contract
  ------------------------------------------------------------------------

542. Enumeration returns directory entries, not unique filenames

     A Search First/Search Next sequence returns every matching
     directory entry; BDOS does not deduplicate entries having the same
     8.3 identity.

     Disposition: REQUIRED

     Evidence: I029; BDOS; IG; I009.

     Conformance: Search a controlled multi-extent file and observe each
     matching extent entry.

543. Matching extents remain separately visible

     Multiple matching extents of one file are returned on separate
     successful calls with their own EX/S2, RC, and allocation fields.

     Disposition: REQUIRED

     Evidence: I029; BDOS; IG; I017.

     Conformance: Enumerate a file exceeding one extent and compare
     returned 32-byte entries.

544. Application-built FCB case is not folded

     BDOS directory matching does not guarantee lowercase-to-uppercase
     canonicalization; applications requiring ordinary CP/M names supply
     canonical uppercase FCB bytes.

     Disposition: NOT GUARANTEED

     Evidence: I029; BDOS; IG; CCP; I023.

     Conformance: Compare uppercase and lowercase application-built FCB
     searches against one uppercase directory entry.

545. Search FCB lifetime

     The FCB storage and relevant search fields used for Search First
     remain valid and unchanged until the corresponding Search Next
     sequence is complete.

     Disposition: REQUIRED

     Evidence: I029; BDOS; IG.

     Conformance: Use stable FCB storage for a multi-result sequence;
     separately diagnose mutation as nonportable.

546. Harmless state-query calls need not end enumeration

     Calls that only return version or current-drive state do not, by
     themselves, terminate an active DRI-compatible Search Next
     sequence.

     Disposition: REQUIRED

     Evidence: I029; BDOS; IG; I026.

     Conformance: Interpose Functions 12 and 25 between successful First
     and Next calls.

547. Search context does not survive program lifecycle reset

     A transient may not rely on Search Next state surviving
     termination, warm boot, disk-system reset, or entry into a later
     transient.

     Disposition: NOT GUARANTEED

     Evidence: I029; BDOS; CCP; I024; I026; I028.

     Conformance: Require each new lifecycle to begin enumeration with
     Search First.

548. Physical enumeration order is not a sort contract

     Repeated searches of unchanged directory state preserve scan order,
     but applications may not require alphabetical order or identical
     order on independently constructed disks.

     Disposition: NOT GUARANTEED

     Evidence: I029; BDOS; IG; I009.

     Conformance: Accept directory-order results and reject tests that
     require alphabetical sorting.

549. Invalid-drive search need not return a result code

     A directory search that encounters invalid or unavailable
     drive/media state may enter the CP/M disk-error presentation path
     instead of returning a Function 17/18 status.

     Disposition: NOT GUARANTEED

     Evidence: I029; BDOS; IG; I025.

     Conformance: Test returned no-match separately from a controlled
     invalid-drive fatal path.

550. Special drive-question search exposes complete directory values

     With FCB dr=‘?’, Search First disables automatic drive selection
     and scans the current drive without ordinary user filtering,
     including allocated and free directory values as documented.

     Disposition: REQUIRED

     Evidence: I029; BDOS; IG; I009.

     Conformance: Continue a controlled dr=‘?’ scan across user bytes
     and an E5h free directory slot.

  ---------------------------------------------------------------------------
   030 - CP/M 2.2 BDOS File Lifecycle, Extent Management, and Metadata State
                             Transition Semantics
  ---------------------------------------------------------------------------

551. Make-to-open lifecycle equivalence

     A successful Make activates an empty FCB for immediate I/O; after
     successful Close, a later Open of that identity reconstructs an
     equivalent usable empty or written file state.

     Disposition: REQUIRED

     Evidence: I030; BDOS; IG; I008; I011.

     Conformance: Exercise Make-only, Make/Close, Make/write/Close, and
     reopen.

552. Working FCB may lead directory metadata

     During a modified open lifecycle, the activated FCB may contain
     newer RC and allocation state than directory Search exposes before
     required Close.

     Disposition: NOT GUARANTEED

     Evidence: I030; BDOS; IG; I011; I029.

     Conformance: Compare the working FCB and Search record before
     Close.

553. Successful Close establishes reopened consistency

     After successful Close, Open, sequential/random access, directory
     extent entries, and Compute File Size describe a mutually
     consistent persistent file.

     Disposition: REQUIRED

     Evidence: I030; BDOS; IG; I008-I013; I029.

     Conformance: Close a grown multi-extent file, reopen it, enumerate
     extents, read boundary markers, and compute size.

554. Reopen reconstructs behavior, not FCB byte identity

     Open reconstructs a usable working FCB from directory state;
     applications may not require incidental or private bytes to equal
     the preceding writer’s FCB.

     Disposition: NOT GUARANTEED

     Evidence: I030; BDOS; IG; I008; I027.

     Conformance: Compare access and documented fields rather than all
     literal FCB bytes.

555. Extents form one logical record stream

     Multiple directory extents sharing a file identity are one logical
     file for sequential crossing, random addressing, reopening, and
     file-size computation.

     Disposition: REQUIRED

     Evidence: I030; BDOS; IG; I010; I011; I013; I029.

     Conformance: Verify records 127-129 through sequential, random,
     search, reopen, and size interfaces.

556. Completed extent survives later extension failure

     Failure to create or allocate a following extent does not
     invalidate records already successfully written and committed in
     the completed extent.

     Disposition: REQUIRED

     Evidence: I030; BDOS; IG; I011; I025.

     Conformance: Fill extent 0 with no slot for extent 1 and verify its
     128 records after the next write fails.

557. Failed growth does not claim a new record

     A failed sequential or random extension must not make the
     unsuccessful target record part of the reopened file length.

     Disposition: REQUIRED

     Evidence: I030; BDOS; IG; I011; I013; I025.

     Conformance: Exhaust directory or allocation space, attempt
     extension, then reopen and compute size.

558. Allocation order is outside lifecycle compatibility

     Compatibility requires sufficient usable allocation reflected in
     FCB/directory state, not DRI’s exact block-search order or
     directory-slot choice.

     Disposition: NOT REQUIRED

     Evidence: I030; BDOS; AG; I011; I017.

     Conformance: Compare content, length, and valid allocation rather
     than exact block numbers.

   031 - CP/M 2.2 BDOS User Area, File Visibility, and Directory Namespace
                                  Semantics
  -------------------------------------------------------------------------

559. User area participates in ordinary file identity

     Ordinary CP/M 2.2 identity combines selected drive, current BDOS
     user, and FCB name/type; identical names in different users are
     distinct objects.

     Disposition: REQUIRED

     Evidence: I031; BDOS; IG; I008; I012.

     Conformance: Create the same 8.3 identity in two users and read
     distinct content.

560. Function 32 user-state contract

     Function 32 uses C=20h; E=FFh returns current user and other E
     values set user modulo 32.

     Disposition: REQUIRED

     Evidence: I031; BDOS; IG; I026.

     Conformance: Query, set 1/31/32, query, and restore.

561. FCB does not carry ordinary user identity

     An ordinary FCB has no user-number field; BDOS applies live
     current-user state when resolving directory operations.

     Disposition: REQUIRED

     Evidence: I031; BDOS; IG; I008; I026.

     Conformance: Hold FCB bytes constant while changing current user
     and repeat lookup.

562. Ordinary lookup has no cross-user fallback

     Search and Open failure in the current user do not trigger lookup
     in user 0 or another user.

     Disposition: REQUIRED

     Evidence: I031; BDOS; IG.

     Conformance: Place the target only in another user and require
     ordinary failure.

563. Make records current-user ownership

     Successful Make creates its directory entry in the current user and
     may create a name that independently exists in another user.

     Disposition: REQUIRED

     Evidence: I031; BDOS; IG; I011; I030.

     Conformance: Make the same exact name under two user numbers and
     inspect entry byte 0.

564. Delete and Rename are current-user scoped

     Exact and wildcard Delete/Rename modify matching entries in the
     current user only; Rename preserves their user number.

     Disposition: REQUIRED

     Evidence: I031; BDOS; IG; I012.

     Conformance: Operate on duplicate names and verify the other user’s
     entry/content remains.

565. User change invalidates retained namespace assumptions

     After changing current user, applications may not assume an
     activated FCB or active ordinary search remains bound to its
     previous user.

     Disposition: NOT GUARANTEED

     Evidence: I031; BDOS; IG; I026; I029; I030.

     Conformance: Require restore/reopen/new Search First after user
     change.

566. Complete-directory search is not public lookup

     FCB dr=‘?’ may enumerate entries across user numbers, but does not
     make those files ordinary Open/Delete/Rename targets in the current
     user.

     Disposition: REQUIRED

     Evidence: I031; BDOS; IG; I009; I029.

     Conformance: Enumerate another-user entry then show ordinary Open
     still fails.

567. CCP USER and BDOS user state are shared

     CCP USER changes BDOS current-user state inherited by subsequent
     commands and transients; DRI CCP accepts USER values 0-15 while
     BDOS supports modulo 32.

     Disposition: REQUIRED

     Evidence: I031; CCP; BDOS; IG; I021; I026.

     Conformance: Issue USER, run a transient Function-32 query, and
     test visibility.

568. User areas are not a security contract

     CP/M 2.2 user areas provide namespace filtering and do not
     guarantee permissions, isolation against complete-directory
     inspection, or modern access control.

     Disposition: NOT REQUIRED

     Evidence: I031; BDOS; IG; AG.

     Conformance: Test namespace results without asserting security
     properties.

  032 - CP/M 2.2 CCP Resident Command Semantics and BDOS Interaction

569. Resident command semantic set

     DRI CP/M 2.2 CCP provides resident DIR, ERA, TYPE, SAVE, REN, and

     Disposition: REQUIRED

570. DIR search and visibility

     DIR lists non-system matches from ordinary current-user BDOS search

     Disposition: REQUIRED

     Evidence: I032; CCP; BDOS; IG; I029; I031.

571. DIR ordering and exact layout

     DIR follows BDOS directory order; alphabetical order and DRI’s

     Disposition: NOT GUARANTEED

     Evidence: I032; CCP; IG; I029.

     Conformance: Validate names/visibility without sorting or
     pixel-exact layout requirements.

572. ERA wildcard confirmation boundary

     ERA deletes exact/partial-wildcard current-user matches without

     Disposition: REQUIRED

     Evidence: I032; CCP; BDOS; IG; I012; I031.

573. ERA read-only attribute is not protection

     Applications may not rely on the CP/M directory read-only attribute

     Disposition: NOT GUARANTEED

     Evidence: I032; CCP; BDOS; IG.

     Conformance: Attempt ERA on a controlled read-only-attributed
     entry.

574. REN resident syntax and validation

     REN accepts an unambiguous new=old pair on one selected drive,
     rejects an existing destination or absent source, and preserves
     current user identity.

     Disposition: REQUIRED

     Evidence: I032; CCP; BDOS; IG; I012; I031.

     Conformance: Test success, collision, missing source, drive
     conflict, and duplicate other-user names.

575. SAVE page mapping

     SAVE n file writes n 256-byte pages beginning at 0100h as 2*n
     sequential 128-byte records and successfully Closes the result.

     Disposition: REQUIRED

     Evidence: I032; CCP; BDOS; IG; I011; I030.

     Conformance: SAVE known memory pages and verify exact file
     length/content.

576. SAVE destructive replacement

     DRI SAVE deletes an existing destination before Make/write; failure
     does not guarantee preservation of the prior file.

     Disposition: NOT GUARANTEED

     Evidence: I032; CCP; BDOS; IG; I030.

     Conformance: Exercise replacement with controlled allocation
     failure.

577. TYPE byte-stream contract

     TYPE sequentially emits stored bytes to console until 1Ah or
     physical EOF and does not promise character-set conversion or
     control-byte sanitization.

     Disposition: REQUIRED

     Evidence: I032; CCP; BDOS; IG; I010.

     Conformance: Test text, empty, embedded controls, 1Ah, multirecord,
     and missing files.

578. CCP USER accepted range

     Resident USER accepts decimal 0-15, changes shared BDOS
     current-user state, and affects subsequent commands/transients;
     higher BDOS user codes are not accepted by DRI CCP USER.

     Disposition: REQUIRED

     Evidence: I032; CCP; BDOS; IG; I026; I031.

     Conformance: Test 0, 1, 15, 16 and a following transient
     Function-32 query.

579. Ordinary resident-command recovery

     Unknown commands, malformed operands, and ordinary file-operation
     failures recover to a usable CCP prompt without transient
     execution.

     Disposition: REQUIRED

     Evidence: I032; CCP; BDOS; IG; I021; I025.

     Conformance: Test token errors, missing files, collision, invalid
     count, and no-space cases.

580. Exact resident output presentation

     Whether BetterCP/M strict mode guarantees DRI’s exact DIR layout
     and diagnostic strings beyond their semantic content remains
     undecided.

     Disposition: POLICY PENDING

     Evidence: I032; CCP; IG.

     Conformance: Corpus-test utilities/scripts that may parse CCP
     output before deciding.

  -------------------------------------------------------------------
  033 - CP/M 2.2 BDOS-BIOS Error Propagation and Recovery Semantics
  -------------------------------------------------------------------

581. Physical failure suspends the BDOS caller

     A final nonzero BIOS READ/WRITE result diverts BDOS into
     operator-error handling; the invoking BDOS call does not deliver an
     ordinary function result until the operator chooses a continuation
     path.

     Disposition: REQUIRED

     Evidence: I033; BIOS; BDOS; AG.

     Conformance: Inject a final BIOS read and write failure and verify
     that the direct caller is suspended at physical-error presentation.

582. Logical failures return without physical-error intervention

     Documented logical file and directory failures return through each
     function’s own result convention without entering Bad Sector
     handling.

     Disposition: REQUIRED

     Evidence: I033; BDOS; IG; AG.

     Conformance: Compare EOF, unwritten-record, capacity, and no-match
     cases with injected BIOS failures and verify distinct
     return/presentation paths.

583. Ignored directory-search result is not validation

     After an ignored physical directory-read failure, a returned Search
     slot code does not guarantee that the caller’s DMA contains a valid
     newly read directory record or that search continuation state is
     coherent.

     Disposition: NOT GUARANTEED

     Evidence: I033; BDOS; BIOS.

     Conformance: Fail the directory read during Search, ignore, and
     inspect the returned slot, DMA record, and continuation behavior
     independently.

584. Ignored directory-update result is not persistence

     After an ignored physical directory-write failure, a
     success-looking Make, Delete, Rename, or Close result does not
     guarantee that the requested directory or allocation change
     persisted.

     Disposition: NOT GUARANTEED

     Evidence: I033; BDOS; BIOS.

     Conformance: Inject pre-transfer directory-write failures and
     compare the returned value with an independently read
     post-operation disk image.

585. Post-ignore affected state is not a continuation contract

     CP/M 2.2 does not guarantee rollback or coherence of the affected
     FCB, DMA contents, directory-search cursor, extent state,
     allocation state, or private BDOS state after an ignored physical
     error.

     Disposition: NOT GUARANTEED

     Evidence: I033; BDOS; IG omission.

     Conformance: Capture every public state object before and after
     ignored failures without treating unchanged or advanced fields as
     success proof.

586. Physical-error abort abandons the interrupted caller

     Control-C at Bad Sector presentation aborts the interrupted BDOS
     path; the transient caller is not resumed at the instruction
     following the call.

     Disposition: REQUIRED

     Evidence: I033; BDOS; CCP; AG; I035.

     Conformance: Place a marker after the BDOS call, inject failure,
     answer with Control-C, and verify the marker is absent and CCP
     recovery occurs.

587. Abort recovery establishes a usable command environment

     The physical-error Control-C route must leave a functioning
     warm-started resident system and CCP command environment, without
     promising preservation of the interrupted application’s state.

     Disposition: REQUIRED

     Evidence: I033; BIOS; BDOS; CCP; AG; I035.

     Conformance: Abort an injected failure, then execute a CCP command
     and an independent healthy BDOS disk operation.

588. Exact recovery internals are not part of the contract

     Exact disk-reset calls, reload sectors, stack/register residue,
     private BDOS caches, retry implementation, and CCP reconstruction
     sequence after a physical-error abort are not required if the
     documented public recovery result is achieved.

     Disposition: NOT REQUIRED

     Evidence: I033; BIOS; BDOS; CCP; AG; I035.

     Conformance: Compare distinct conforming implementations by public
     post-restart behavior rather than internal call sequence or
     addresses.

  ---------------------------------------------------------------------------
   034 - CP/M 2.2 Memory Layout, System Area, and Transient Program Boundary
                                   Semantics
  ---------------------------------------------------------------------------

589. Loader ceiling and overlay TPA are distinct

     The largest COM image accepted by the active CCP loader may be
     smaller than the configured TPA advertised through the 0005h jump
     operand, because the loader may retain CCP and its return
     environment while an executing transient may deliberately overlay
     them.

     Disposition: REQUIRED

     Evidence: I034; MEMORY; CCP; AG; I028.

     Conformance: Compare the first rejected COM record with runtime
     writes below the advertised 0006h ceiling using a safe private
     stack and recovery path.

590. CCP overlay invalidates ordinary RET assumptions

     A transient that overwrites active CCP code, data, or its supplied
     return environment cannot rely on ordinary RET into that
     environment; it must retain a valid recovery route such as
     programmed warm restart.

     Disposition: REQUIRED

     Evidence: I034; MEMORY; CCP; BIOS; AG.

     Conformance: Overwrite controlled CCP bytes after adopting a
     private stack, avoid RET, invoke WBOOT, and verify a usable command
     environment is restored.

591. System ownership is an application obligation

     CP/M 2.2 provides no memory-protection barrier between transient
     and system regions. A physically successful write to page zero,
     CCP, BDOS, or BIOS does not guarantee that the overwritten service,
     return path, or restart remains valid.

     Disposition: NOT GUARANTEED

     Evidence: I034; MEMORY; BDOS; BIOS; AG.

     Conformance: Test documented accesses normally and treat
     destructive writes only as isolated takeover cases with an
     independently retained recovery path.

592. Entry-stack storage may occupy overlayable memory

     The valid transient entry return word and surrounding stack may
     reside in memory that an overlaying application otherwise intends
     to use; exact stack placement, capacity, and survival after overlay
     are not guaranteed.

     Disposition: NOT GUARANTEED

     Evidence: I034; MEMORY; CCP; I001; I028.

     Conformance: Vary entry stack placement; require immediate RET, but
     require an overlaying program to establish its own stack before
     consuming that region.

593. Cold BOOT public postcondition

     A configured cold BOOT shall establish usable BIOS, BDOS, and CCP
     service, valid public page-zero gateways, the configured initial
     IOBYTE policy, and CCP entry with drive A selected.

     Disposition: REQUIRED

     Evidence: I035; BIOS; BDOS; CCP; IG; AG.

     Conformance: From an arbitrary pre-BOOT public-state pattern,
     invoke the configured BOOT entry and verify a usable A-drive
     CCP/BDOS environment and valid 0000h/0005h gateways; do not require
     a particular loader or sign-on.

594. Cold BOOT does not promise blanket memory clearing

     Applications shall not assume that cold BOOT clears every TPA,
     zero-page, or otherwise unspecified RAM byte.

     Disposition: NOT GUARANTEED

     Evidence: I035; BIOS; MEMORY; AG.

     Conformance: A system may retain or overwrite unspecified memory
     during BOOT; applications must rely only on documented post-BOOT
     state.

595. WBOOT command-environment reconstruction

     WBOOT shall nonreturningly restore or equivalently reconstruct a
     usable CCP environment, the public 0000h/0005h gateways, and
     default DMA state.

     Disposition: REQUIRED

     Evidence: I035; BIOS; CCP; MEMORY; AG.

     Conformance: Corrupt safe gateway operands and select a nondefault
     DMA, then enter WBOOT and verify reconstructed gateways, DMA 0080h,
     and a usable CCP.

596. Residual state across WBOOT

     Survival of arbitrary TPA/scratch bytes, pending console input,
     application FCB/search state, and private BIOS/BDOS/CCP state
     across WBOOT is not part of the CP/M 2.2 compatibility contract.

     Disposition: NOT GUARANTEED

     Evidence: I035; BIOS; BDOS; CCP; MEMORY; IG; AG.

     Conformance: Applications shall remain correct whether such
     unspecified state survives or is overwritten; implementations need
     not reproduce the reference residue.

597. Console-pending state across WBOOT

     CP/M 2.2 does not guarantee preservation of a character reported
     pending but not consumed before WBOOT.

     Disposition: NOT GUARANTEED

     Evidence: I035; BIOS; IG; AG.

     Conformance: After WBOOT, either loss or BIOS-defined retention of
     previously pending unconsumed console input is compatible unless
     the configured BIOS interface separately promises otherwise.

598. BIOS vector is a public runtime ABI

     The standard CP/M 2.2 BIOS vector of seventeen entries is a public
     runtime interface available to compatible software, not merely an
     internal BDOS implementation detail.

     Disposition: REQUIRED

     Evidence: I036; BIOS; AG; IG.

     Conformance: Invoke documented BIOS vector entries through the
     configured vector and verify the documented call interface.

599. DPH structures are compatibility-visible

     The BIOS Disk Parameter Header and its documented referenced
     structures are visible parts of the runtime disk interface.

     Disposition: REQUIRED

     Evidence: I036; BIOS; AG.

     Conformance: Inspect DPH-derived runtime structures and verify
     documented fields required by compatible software.

600. Direct BIOS calls expose raw device behavior

     Direct BIOS disk calls operate below BDOS file-system services and
     do not provide BDOS editing, file-system protection, or fatal-error
     presentation.

     Disposition: REQUIRED

     Evidence: I036; BIOS; BDOS; SYSGEN; AG.

     Conformance: Compare direct BIOS access with BDOS operations and
     verify that BIOS behavior remains at the device layer.

601. BIOS implementation details remain profile-specific

     BIOS base addresses, physical devices, buffering strategies,
     controller behavior, and vendor-private extensions are not
     universal compatibility requirements.

     Disposition: NOT GUARANTEED

     Evidence: I036; BIOS; AG.

     Conformance: Require documented BIOS behavior while permitting
     implementation-specific hardware abstraction choices.

602. Function 40 selector and input

     BDOS Function 40 is Random Write with Zero Fill. It takes DE
     pointing to an activated FCB whose random-record fields select the
     target, and writes the 128-byte record from the current DMA
     address.

     Disposition: REQUIRED

     Evidence: I037; BDOS; FILE; AG.

     Conformance: Open or create a controlled file, select a random
     record in the FCB, set DMA, call Function 40, and verify the target
     record.

603. Function 40 allocation-block zero fill

     When Function 40 allocates a physical allocation block for a target
     random record, unwritten records in that newly allocated block
     preceding the target are written as zero-filled 128-byte records.

     Disposition: REQUIRED

     Evidence: I037; BDOS; FILE; AG.

     Conformance: Write record 10 of a new file on a multi-record
     allocation-block disk and verify preceding record 9 reads
     successfully as 128 zero bytes.

604. Function 40 is not universal sparse-hole materialization

     Function 40 does not guarantee that every logical hole before a
     distant target record becomes allocated or readable; zero fill is
     bounded by allocation-block processing and configured file-system
     geometry.

     Disposition: NOT GUARANTEED

     Evidence: I037; BDOS; FILE; IG; AG.

     Conformance: Vary allocation-block size and distant target records;
     applications shall not require holes outside allocated blocks to
     read as zeros.

605. Function 40 result family

     Function 40 returns the CP/M 2.2 random-write result family,
     including zero on success, 02h when storage is unavailable, and 06h
     when the 24-bit random record is outside the supported range.

     Disposition: REQUIRED

     Evidence: I037; BDOS; FILE; IG; AG.

     Conformance: Test success, exhausted storage, and nonzero R2
     overflow with controlled images and verify the corresponding codes.

606. BIOS character services are raw device interfaces

     BIOS reader, console, punch, and list services provide raw logical
     character-device interfaces. BDOS console functions may add
     buffering, editing, echo, and formatting above these BIOS paths.

     Disposition: REQUIRED

     Evidence: I038; BIOS; BDOS; IG; AG.

     Conformance: Compare direct BIOS character calls with BDOS console
     functions and verify the documented layering boundary.

607. Character devices remain distinct runtime paths

     Reader, console, punch, and list devices are separate CP/M 2.2
     character-service paths and are not interchangeable through
     implicit routing.

     Disposition: REQUIRED

     Evidence: I038; BIOS; BDOS; AG.

     Conformance: Exercise each character path independently and verify
     that the selected device service is used.

608. IOBYTE reassignment is runtime visible

     Changes to the CP/M 2.2 IOBYTE device assignment are immediately
     visible to applications and BIOS routines that consult the
     assignment.

     Disposition: REQUIRED

     Evidence: I038; BIOS; BDOS; AG.

     Conformance: Change IOBYTE assignments and verify subsequent device
     operations use the updated mapping.

0609. IOBYTE access coherence

      Direct memory location 0003h and BDOS Functions 7/8 expose one coherent
      runtime IOBYTE value; a change through either supported access is visible
      to subsequent application and configured BIOS device operations.

      Disposition: REQUIRED

      Evidence:    I039; I038; IOBYTE; DEVICE; BDOS; BIOS; AG.

      Conformance: Set values through Function 8 and direct access, query
                   through the other path, and verify configured device routing.


0610. Field-preserving assignment changes

      Changing one logical device assignment replaces only its designated
      two-bit IOBYTE field and preserves the other three fields.

      Disposition: REQUIRED

      Evidence:    I039; I038; IOBYTE; DEVICE; STAT; AG.

      Conformance: Begin with distinct field values, change each assignment
                   independently, and verify the remaining six bits.


0611. IOBYTE assignment does not validate device presence

      Storing a valid IOBYTE value does not guarantee that the selected
      physical device exists or that I/O succeeds; availability and failure
      are configured BIOS/device-profile behavior.

      Disposition: NOT GUARANTEED

      Evidence:    I039; I038; IOBYTE; DEVICE; BIOS; IG; AG.

      Conformance: Accept valid assignment states while testing unavailable
                   mappings according to the declared device profile.


0612. STAT device-assignment semantics

      A CP/M 2.2 profile providing DRI-compatible STAT configuration shall
      display current logical mappings, change one field without altering
      others, and reject unknown assignments without changing IOBYTE.

      Disposition: REQUIRED

      Evidence:    I039; I038; IOBYTE; DEVICE; STAT; IG; AG.

      Conformance: Display fields, make valid changes, attempt an invalid
                   name, and compare IOBYTE before and after each action.


0613. Parameterized disk-structure coherence

      Each advertised CP/M 2.2 drive profile shall provide mutually coherent
      DPH, DPB, directory, allocation-map, ALV, logical-sector, and capacity
      semantics.

      Disposition: REQUIRED
      Evidence:    I040 STORAGE DISK BDOS BIOS subsystem IG AG; DPB040;
                   STAT; raw matrix
      Conformance: validate empty, populated, and nearly full media against
                   every public field.


0614. DPB-dependent directory allocation-map width

      Directory entries use sixteen one-byte allocation numbers when DSM is
      below 256 and eight little-endian word allocation numbers for larger
      disks.

      Disposition: REQUIRED
      Evidence:    I040 STORAGE DISK BDOS BIOS subsystem IG AG; disk
                   definitions
      Conformance: exercise both DSM classes.


0615. Logical directory placement

      Directory entries occupy DPB-reserved allocation blocks and are
      transferred as 128-byte logical sectors; their raw physical offsets
      depend on OFF and sector translation.

      Disposition: REQUIRED
      Evidence:    I040 STORAGE DISK BDOS BIOS subsystem IG AG; BIOS040;
                   matrix
      Conformance: parse a nonidentity translation profile without assuming
                   contiguous physical directory sectors.


0616. Raw-format universality

      CP/M 2.2 does not guarantee one raw disk image layout, physical
      geometry, sector numbering, skew table, or host-sector representation
      across systems.

      Disposition: NOT GUARANTEED
      Evidence:    I040 STORAGE DISK BDOS BIOS subsystem IG AG; two
                   definitions
      Conformance: accept distinct declared profiles implementing the same
                   logical interfaces.


0617. Direct-structure caller responsibility

      A direct disk caller must use the configured BIOS and its returned
      disk parameters/translation and receives no BDOS allocation,
      directory, or open-file protection for raw writes.

      Disposition: REQUIRED
      Evidence:    I040 STORAGE DISK BDOS BIOS subsystem IG AG; SYSGEN;
                   BIOS040
      Conformance: compare a configured direct read with BDOS access and
                   reject hard-coded foreign geometry.


0618. Damaged-directory recovery

      CP/M 2.2 does not guarantee automatic repair or deterministic
      ownership when directory allocation maps conflict or contain otherwise
      corrupt metadata.

      Disposition: NOT GUARANTEED
      Evidence:    I040 STORAGE DISK BDOS BIOS subsystem IG AG; damaged
                   matrix
      Conformance: detect/report corrupt fixtures without requiring a
                   particular repair choice.

041 - CP/M 2.2 Direct System Access and Undocumented Application Interface Compatibility Semantics
----------------------------------------------------------------------------


0619. Private BDOS target is not an application gateway

      The address stored in the 0005h JMP operand identifies the configured
      BDOS entry and memory ceiling, but an application is not guaranteed
      that calling that target directly is equivalent to CALL 0005h or
      remains valid across conforming implementations and configurations.

      Disposition: NOT GUARANTEED

      Evidence:    I041; SYSTEM; BDOS; BIOS; MEMORY; IG; AG; DIRECT41;
                   XSUB; AS0COM.

      Conformance: Relocate or wrap the BDOS implementation while preserving
                   CALL 0005h and verify conforming applications continue
                   to operate; do not accept a private-target caller as a
                   general conformance requirement.
