OBJECTIVE

Perform deeper validation of the CP/M 2.2 communications compatibility
boundary.

Previous investigations established:

- CP/M communications software compatibility requirements;
- software ecosystem assumptions;
- BIOS and device interface behavior;
- conformance validation requirements;
- remaining closure requirements from the engineering gap assessment.

Investigation 065 determines whether communications compatibility
requirements are sufficiently understood for specification release.

Determine:

- which communications behaviors are portable CP/M compatibility
  requirements;
- which behaviors belong to hardware or device profiles;
- whether timing, transfer, and failure behavior reveal additional
  compatibility requirements.


COMPATIBILITY STANDARD

Consider:

- documented CP/M 2.2 behavior;
- Digital Research implementation behavior;
- common CP/M programming practices;
- historically significant communications software dependencies.

Distinguish between:

- CP/M-visible communication semantics;
- BIOS/device interface behavior;
- hardware-specific communication behavior.

Do not assume modem or serial hardware behavior is part of the CP/M
compatibility contract without evidence.

INVESTIGATION QUESTIONS


1. COMMUNICATIONS SOFTWARE CORPUS

Identify representative communications software.

Record:

- software name;
- version where available;
- source/archive location;
- category;
- platform assumptions;
- evidence collected.


2. COMMUNICATION INTERFACE USAGE

Determine:

- BDOS usage;
- BIOS character-device usage;
- direct hardware access;
- device assumptions;
- software-visible behavior.


3. TRANSFER VALIDATION

Determine:

- file-transfer assumptions;
- protocol behavior;
- successful transfer behavior;
- interoperability requirements.


4. FAILURE BEHAVIOR

Determine:

- timeout behavior;
- interrupted transfers;
- device failures;
- recovery behavior;
- user-visible error handling.


5. TIMING AND PERFORMANCE ASSUMPTIONS

Determine:

- polling assumptions;
- delay-loop behavior;
- baud-rate dependencies;
- CPU-speed assumptions;
- whether behavior affects compatibility.


6. HARDWARE PROFILE BOUNDARY

Determine:

- which behaviors belong to CP/M compatibility;
- which belong to BIOS/device profiles;
- which are machine-specific.


7. EXPERIMENTAL REQUIREMENTS

Create communications validation records.

Each record must include:

- software tested;
- communication scenario;
- environment;
- procedure;
- observed behavior;
- compatibility conclusion.


8. CONTROLLED TEST MATRIX

Include:

- normal transfers;
- failed transfers;
- interrupted transfers;
- device unavailable cases;
- boundary timing cases.
