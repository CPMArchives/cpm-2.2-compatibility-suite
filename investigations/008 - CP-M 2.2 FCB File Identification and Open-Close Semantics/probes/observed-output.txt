Investigation 008 raw observations
==================================

Question tested
---------------

What FCB fields do DRI CP/M 2.2 functions 15 and 16 consume, return, preserve,
or persist for successful, failed, wildcard, explicit-drive, and extent cases?

Probe
-----

Source: FCB008.ASM
Binary SHA-256: b42b6416579a25b849af29d2001bb239cd4a49853b8dd85e5bae0170e709d95e

Expected behavior
-----------------

Documented expectations were: existing files open with directory code 0-3;
missing files return FFh; wildcard open activates the first match; directory
metadata fills the FCB; explicit B selection is temporary; an unchanged file
need not be closed; a dirty close persists FCB directory information; and a
missing dirty close returns FFh. Caller CR was expected to remain AA because
DRI source copies only bytes 0-31 during open.

Observed behavior and interpretation
------------------------------------

1. OPEN-A returned directory code 0 and replaced directory-derived bytes
   through byte 31 while preserving caller CR=AA at byte 32.
2. MISSING returned FF. DRI cleared input S2 before the failed match; the
   name, extent, S1, RC, allocation sentinels, and CR otherwise survived.
3. WILD activated OPENME.DAT and replaced '?' with the actual matched name.
4. OPEN-B succeeded, retained FCB drive code 2 after DRI restored A as the
   current default, and copied B's directory metadata.
5. EXTENT1 returned directory code 3, retained requested EX=1, and returned
   extent-specific RC/allocation state for the 20000-byte file.
6. CLEANCL returned 0. The DRI private high S2 no-write bit remained set, so
   source analysis shows that no directory search/write was performed.
7. DIRTYCL cleared that private bit and changed RC to 2. Close returned the
   actual directory code 1. REOPEN also returned 1 and recovered RC=2,
   proving persistence.
8. MISSCL returned FF for a dirty FCB whose name had no directory match.

After execution, image hashes were:

  A 8e128b0ce28d54a7967e0d02f3596d27b0adb677a8c6d7d68857b888ce8793bc
  B 91306c2f4067f974b001df5cfd174ecbfd710746cb9a076b7d75e086f8b9ee73

B was unchanged. Host-side cpmtools displayed CLOSE.DAT as 146 bytes after
RC changed to 2 because cpmcp had placed an exact-byte-count extension in the
reserved S1 field. That convention is not DRI CP/M 2.2 evidence. DRI's manual
reserves S1 for internal use, and DRI BDOS ignores S1 when matching.

Limitations
-----------

The experiment used a single-byte allocation-map disk format and drives A/B.
It does not establish double-byte allocation-map representation, directory
ordering across other formats, or exact host-tool S1 conventions. It did not
perform BDOS write calls; the dirty-close condition was established directly
in the in-memory FCB on a disposable copy. It does not investigate make,
delete, search enumeration, sequential I/O, media errors, disk-full behavior,
or close allocation-map conflicts.
