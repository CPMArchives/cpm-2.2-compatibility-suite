Create Investigation 066 as a new evidence report with its own directory

OBJECTIVE

Validate CP/M 2.2 physical fault handling and recovery behavior to
determine whether storage failures reveal additional compatibility
requirements.

Previous investigations established:

- CP/M 2.2 storage semantics;
- BDOS file-system behavior;
- BIOS disk interface behavior;
- error propagation requirements;
- conformance validation requirements.

Investigation 066 determines whether failure behavior during physical
storage operations is sufficiently understood for compatibility
specification release.

Determine:

- which physical fault behaviors are visible to CP/M software;
- which recovery behaviors are compatibility requirements;
- which behaviors belong to hardware or storage profiles;
- whether additional validation is required.


COMPATIBILITY STANDARD

Consider:

- documented CP/M 2.2 behavior;
- Digital Research implementation behavior;
- common CP/M programming practices;
- historically significant software dependencies.

Distinguish between:

- CP/M-visible error semantics;
- BIOS/storage-layer behavior;
- physical hardware failure behavior.

Do not assume internal recovery mechanisms are compatibility
requirements without evidence.

INVESTIGATION QUESTIONS


1. FAULT SCENARIOS

Identify representative physical fault conditions.

Include:

- read failures;
- write failures;
- unavailable media;
- interrupted operations;
- partial completion cases.


2. ERROR PROPAGATION

Determine:

- how failures propagate through BIOS;
- how failures propagate through BDOS;
- what applications observe;
- what software can depend upon.


3. RECOVERY BEHAVIOR

Determine:

- retry behavior;
- abort behavior;
- warm-start behavior;
- user-visible recovery paths.


4. FILE-SYSTEM CONSISTENCY

Determine:

- directory consistency after failures;
- allocation consistency;
- partial writes;
- recovery expectations.


5. SOFTWARE IMPACT

Determine:

- whether historical software depends on specific failure behavior;
- whether applications distinguish failure modes;
- whether behavior affects compatibility.


6. HARDWARE PROFILE BOUNDARY

Determine:

- which behaviors belong to CP/M compatibility;
- which belong to storage-device profiles;
- which are implementation choices.


7. EXPERIMENTAL REQUIREMENTS

Create physical fault validation records.

Each record must include:

- fault scenario;
- operation tested;
- environment;
- procedure;
- observed behavior;
- compatibility conclusion.


8. CONTROLLED TEST MATRIX

Include:

- normal operation;
- injected failure;
- interrupted operation;
- recovery attempt;
- repeated failure cases.
