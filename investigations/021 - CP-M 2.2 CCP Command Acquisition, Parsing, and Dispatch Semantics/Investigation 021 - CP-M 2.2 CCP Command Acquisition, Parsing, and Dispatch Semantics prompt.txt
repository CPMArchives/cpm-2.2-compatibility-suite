INVESTIGATION 021 — CP/M 2.2 CCP Command Acquisition, Parsing, and
Dispatch Semantics

Continue the BetterCP/M CP/M 2.2 compatibility investigation series.

Investigation 020 is complete.

The authoritative Compatibility Ledger is now:

    02 Compatibility Ledger - Investigation 020.txt

It incorporates findings through Investigation 020 and currently ends at
entry 0474.

Do not modify the Compatibility Ledger.

Do not modify any previous investigation report, architecture document,
roadmap, source archive, or other pre-existing BetterCP/M file.

Create Investigation 021 as a new evidence report with its own directory
and associated probe/harness artifacts.

This is an EVIDENCE INVESTIGATION, not BetterCP/M implementation work.


OBJECTIVE

Establish the CP/M 2.2 Console Command Processor command-acquisition,
lexical parsing, command classification, and dispatch contract.

This investigation begins the systematic CCP compatibility campaign.

Concentrate on the path:

    CCP prompt
        |
        v
    command-line acquisition
        |
        v
    lexical normalization/parsing
        |
        v
    command-name recognition
        |
        +--------------------+
        |                    |
        v                    v
    resident command     transient command
        |                    |
        v                    v
    resident dispatch    transient lookup path

The purpose is to determine the common command-processing machinery before
separate investigations examine the detailed semantics of individual
resident commands or transient-program loading.

This investigation should establish:

    - how the CCP obtains a command line;
    - what constitutes an empty command;
    - how command names and operands are separated;
    - how whitespace is treated;
    - how case is treated;
    - how drive prefixes are recognized at command level;
    - how the CCP recognizes resident commands;
    - how it distinguishes resident from transient commands;
    - what syntactic state is passed into those two paths;
    - what happens for malformed or unrecognized command input;
    - which observed behaviors are documented requirements, DRI CCP
      implementation behavior, ecosystem-relevant behavior, or incidental
      details.

Do NOT attempt to specify all resident commands in this investigation.

Do NOT attempt to specify the complete transient-program search/load process
in this investigation.

Those should be investigated separately after the common CCP parsing and
dispatch machinery is understood.

SCOPE BOUNDARY

Investigation 021 is about the COMMON CCP command-processing path.

It includes:

    command acquisition
    command-line normalization
    tokenization
    command-name parsing
    drive-prefix parsing at command level
    resident-command recognition
    resident/transient classification
    generic syntax rejection
    unrecognized-command handling up to the point where the transient
    lookup mechanism becomes command-specific

It does not attempt a complete investigation of:

    DIR
    ERA
    REN
    SAVE
    TYPE
    USER

or any other resident command individually.

It also does not attempt a complete investigation of:

    COM filename construction
    drive search

QUESTIONS TO RESOLVE


1. CCP COMMAND-LOOP ENTRY

Determine the externally relevant state when the CCP is ready to accept a
new command.

Establish:

- how control reaches the CCP after cold BOOT;
- how control reaches the CCP after WBOOT;
- how control reaches the CCP after ordinary transient RET termination;
- whether those paths enter the same command-reading loop;
- what drive state is displayed/used;
- what user-number state is active;
- whether CCP performs disk reset or login operations before every command
  or only on particular entry paths;
- what state from a previous command is intentionally preserved.

Do not duplicate BOOT/WBOOT propositions from Investigation 020.

The purpose is to establish the CCP side of the handoff.


2. COMMAND PROMPT

Determine the CP/M 2.2 CCP prompt semantics.

Establish:

- the documented/reference prompt representation;
- whether the current drive letter is part of the prompt;
- whether the prompt contains `>`;
- whether the user number is displayed;
- when the prompt is emitted;
- whether a new prompt follows an empty command;
- whether prompt case is fixed;
- whether exact spacing is compatibility-relevant;
- whether prompt generation is documented or merely DRI CCP behavior.

Distinguish semantic prompt information from exact presentation details.

If exact DRI prompt text is not established as a compatibility requirement,
do not classify it as REQUIRED merely because historical CP/M prints it.


3. COMMAND-LINE ACQUISITION

Determine how the DRI CCP acquires a command line.

Trace:

- which BDOS console service is used;
- buffer location and size;
- maximum accepted command length;
- how the buffer is initialized;
- how the terminating Return/CR is handled;
- whether LF is involved;
- whether the CCP itself performs editing or relies upon BDOS buffered
  console input;
- what happens at maximum length;
- whether the command reader preserves or discards the terminating
  character.

Cross-check Investigation 006.

Do not duplicate BDOS buffered-input semantics. Identify which consequences
belong specifically to the CCP command environment.


4. EMPTY COMMANDS

Determine what the CCP considers an empty command.

Test separately:

    CR only
    one space then CR
    several spaces then CR
    TAB where the input environment permits it
    combinations of spaces and TABs if relevant

Establish:

- whether an empty line simply causes another prompt;
- whether a whitespace-only line is equivalent to empty;
- whether disk or other state changes;
- whether any error is printed;
- whether the command parser reaches resident/transient lookup.

Do not assume all ASCII whitespace is interchangeable unless source or
experiment establishes it.


5. COMMAND-LEADING WHITESPACE

Determine whether leading blanks before the command name are:

    accepted and skipped
    retained
    rejected
    treated as an empty command
    interpreted in another way

Test multiple leading blanks.

If TAB is accepted as command-line input, test it independently rather than
assuming it is equivalent to SPACE.

Trace the DRI CCP source to determine the exact parser behavior.


6. COMMAND-NAME TOKENIZATION

Determine how the CCP identifies the command-name token.

Establish:

- permitted characters;
- maximum meaningful command-name length;
- termination by SPACE;
- termination by drive colon;
- termination by period;
- termination by other punctuation;
- behavior with multiple spaces;
- behavior with no operand;
- behavior with characters after the apparent command token;
- whether the parser constructs an FCB-like representation internally.

Test boundary cases chosen from source/documentation rather than an arbitrary
ASCII fuzzing campaign.


7. CASE NORMALIZATION

Determine precisely where and when the DRI CCP converts command input to
uppercase.

Establish:

- whether the entire command line is uppercased during acquisition;
- whether only parsed tokens are uppercased;
- whether command names are case-insensitive because of conversion;
- whether operands are converted at the same stage;
- whether punctuation is unaffected;
- whether lowercase input is possible in the reference environment;
- whether case conversion is a documented CP/M contract or DRI CCP behavior.

Cross-check Investigation 001's findings concerning uppercase command tails
and default FCBs.

If the reference console path prevents lowercase from reaching CCP, use
controlled injection or a suitable fixture rather than inferring behavior.


8. COMMAND-SEPARATING WHITESPACE

Determine the treatment of whitespace between command name and operands.

Test, where meaningful:

    one SPACE
    multiple SPACEs
    TAB
    SPACE/TAB combinations

Establish:

- what terminates the command name;
- how many separator characters are skipped;
- whether separators survive into later operand parsing;
- relationship to the leading blank placed in the transient command tail;
- relationship to default-FCB construction.

Be careful to distinguish the CCP's internal input buffer from the final
transient command tail at 0080h.


9. DRIVE PREFIX BEFORE COMMAND

Investigate command forms such as:

    B:
    B:DIR
    B:FOO
    B:FOO ARG

Determine whether CP/M 2.2 CCP permits a drive prefix before a command name
and, if so:

- whether `B:` alone changes the current drive;
- whether `B:COMMAND` executes COMMAND with B as current/default drive;
- whether the drive change persists after the command;
- whether resident and transient commands behave identically;
- when BDOS Function 14 is invoked;
- what happens for an invalid drive letter;
- what happens for malformed prefixes.

Do not confuse command-level drive selection with an operand drive prefix
such as:

    DIR B:*.COM

Those are separate parser roles.


10. DRIVE-ONLY COMMAND

Investigate the drive-selection form independently.

At minimum test:

    A:
    B:
    current-drive:
    unavailable-drive:
    malformed-letter:
    multiple-colon forms where justified

Establish:

- whether drive-only selection is a special CCP command path;
- whether it uses the same command parser;
- whether it changes BDOS current drive;
- whether the prompt changes immediately;
- whether it performs disk login;
- error behavior for an unavailable drive;
- relationship to page-zero location 0004h.

Cross-check Investigation 007.

Do not duplicate Function 14/25 propositions; establish the CCP semantics
built on them.


11. RESIDENT-COMMAND RECOGNITION

Identify the resident command names recognized by the DRI CP/M 2.2 CCP.

Determine from documentation and DRI source the exact set applicable to this
CCP version.

Likely names must be verified rather than assumed, including such commands
as:

    DIR
    ERA
    REN
    SAVE
    TYPE
    USER

Establish:

- exact recognized names;
- whether abbreviations are accepted;
- whether longer strings sharing a prefix are accepted or rejected;
- whether recognition requires an exact token match;
- whether case normalization precedes recognition;
- whether resident-command recognition precedes transient-file lookup;
- whether a `.COM` suffix can force transient interpretation of a name that
  matches a resident command.

Do not investigate each command's complete semantics here.

The result should define only recognition and dispatch.


12. RESIDENT-COMMAND PRECEDENCE

Determine what happens if a transient `.COM` file has the same basename as a
resident command.

For example, using a controlled scratch disk if safe:

    DIR.COM
    TYPE.COM
    SAVE.COM

Determine:

- whether the resident command always wins;
- whether explicit `.COM` changes precedence;
- whether a drive prefix changes precedence;
- whether user area changes precedence;
- whether another syntax can force execution of the transient.

Preserve before/after disk images.

Do not install experimental files into authoritative project disks without
working from copies.


13. RESIDENT DISPATCH BOUNDARY

Trace the DRI CCP from successful resident-name recognition to the selected
resident routine.

Determine:

- what parsed state is passed;
- whether operands are reparsed by individual resident commands;
- whether default FCB construction occurs before or after resident
  recognition;
- whether command-tail construction occurs for resident commands;
- whether the transient entry environment at 005Ch/006Ch/0080h is built
  even when no transient will run;
- which state is common and which is command-specific.

This is important for separating common CCP semantics from later resident
command investigations.


14. TRANSIENT DISPATCH BOUNDARY

Trace the DRI CCP from failure to recognize a resident command to the point
where transient-program lookup begins.

Determine:

- what representation of the command name exists at this boundary;
- whether `.COM` has already been supplied or parsed;
- whether a drive has been resolved;
- whether default FCBs have been constructed;
- whether the command tail has been constructed;
- what current-drive/user state is in effect;
- what generic validation has already occurred.

STOP the investigation at the point where detailed transient file lookup and
loading begin.

Do not turn Investigation 021 into the full transient-loader investigation.


15. COMMAND NAMES WITH PERIODS AND EXTENSIONS

Determine generic parser treatment of forms such as:

    FOO
    FOO.COM
    FOO.TXT
    DIR.COM
    B:FOO.COM

Establish:

- whether an explicit extension is permitted in command position;
- whether `.COM` is accepted, ignored, rejected, or incorporated;
- whether a non-COM extension is rejected before transient lookup;
- whether resident recognition occurs before or after extension handling;
- whether the behavior is documented or DRI-specific.

This question may overlap the transient dispatch boundary but should not
expand into actual COM loading.


16. MALFORMED COMMAND SYNTAX

Identify generic syntax errors recognized before individual resident-command
semantics or transient lookup.

Use source analysis to choose meaningful cases.

Possible cases include:

    invalid drive prefix
    misplaced colon
    multiple colons
    invalid command-name punctuation
    excessive command token length
    malformed extension
    extra unexpected token structure

Determine:

- which malformed forms are rejected by the common parser;
- which are allowed through to resident commands;
- which are treated as transient names and fail later;
- whether a generic error message is produced;
- what state changes survive the failure.

Do not fuzz every possible byte.


17. UNRECOGNIZED COMMAND

Determine the common behavior for a syntactically valid command name that is
not resident.

Use a deliberately nonexistent name.

Establish:

- whether CCP immediately reports an error or attempts transient lookup;
- what file specification it attempts to use;
- whether current drive/user area are involved;
- what happens after lookup failure;
- exact error text and echo behavior in DRI CP/M;
- whether exact presentation is documented or merely conventional;
- whether the command loop then resumes normally.

The detailed lookup algorithm belongs to a later investigation; this test
should identify only the externally visible common failure path and the
boundary into lookup.


18. ERROR PRESENTATION

Catalog generic CCP parser/dispatch error presentation separately from the
semantics of individual resident commands.

Determine:

- whether the offending command/token is echoed;
- whether `?` is used;
- placement of CR/LF;
- whether errors distinguish malformed syntax from missing transient;
- whether the current drive prompt is immediately redisplayed;
- whether exact wording/punctuation is documented;
- whether errors alter drive/user state.

Classify exact text conservatively.

A famous or familiar DRI presentation is not automatically a REQUIRED
compatibility behavior.


19. COMMAND BUFFER SIZE AND BOUNDARIES

Determine the maximum CCP command line accepted by the documented/reference
environment.

Establish:

- buffer capacity;
- whether the limit is inherited directly from BDOS Function 10;
- whether the CCP imposes a smaller limit;
- whether the CR is counted;
- whether truncation, bell, rejection, or another behavior occurs at the
  limit;
- whether the final transient command-tail limit is identical to the CCP
  input-buffer limit.

Cross-check Investigation 001's 0080h command-tail representation and
Investigation 006's buffered-input semantics.

Do not assume those limits are identical without evidence.


20. CCP INTERNAL PARSER STATE VERSUS EXTERNAL CONTRACT

Trace enough DRI CCP source to understand parser operation, but distinguish
carefully between:

    internal implementation
        and
    externally observable compatibility behavior

Examples of internal details that should not automatically become ledger
requirements include:

    exact CCP RAM addresses
    internal labels
    temporary buffer placement
    exact register allocation
    exact call graph
    exact loop structure
    exact comparison order

Propose ledger entries only for behavior software or the command user can
observe, or behavior required at an established CP/M component boundary.


21. CONTROLLED COMMAND-PARSER HARNESS

Construct a deterministic harness capable of submitting command lines to the
reference CCP and preserving raw output.

Prefer automated input over manually typed experiments.

The harness should make it practical to test a matrix including, where
supported:

    empty line
    spaces-only line
    lowercase command
    mixed-case command
    leading spaces
    multiple separators
    drive-only command
    drive-prefixed resident command
    drive-prefixed nonexistent transient
    exact resident name
    resident-name prefix
    resident-name suffix
    explicit `.COM`
    non-COM extension
    nonexistent command
    selected malformed forms

Record exact input bytes and exact console output.

Where the emulator or normal BDOS console path transforms input before CCP
sees it, document that fact and use a controlled injection fixture if needed

Record:

    disk/user context

FINAL GOAL

Investigation 021 should answer this question precisely:

    Given a line of console input at the CP/M 2.2 command prompt, how does
    the DRI CCP acquire, normalize, parse, classify, and dispatch that line
    before the semantics of a particular resident command or the detailed
    transient-program loader take over?

The result should define the common CP/M 2.2 command-processing boundary
rigorously enough that subsequent investigations can study resident commands
and transient loading without repeatedly rediscovering or conflating the
shared CCP parser behavior.
